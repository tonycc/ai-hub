## 0. 文档用途

本文档用于统一后续产品设计、技术设计和代码开发的基本约束，回答以下问题：

1. 统一后台解决什么问题，不解决什么问题。
2. 平台与单个应用之间如何分工。
3. 单个应用如何划分、如何接入平台、如何拥有自己的数据。
4. 后端模块、数据库、接口、事件、工作流和 AI 能力如何设计。
5. 企业语义、本体、业务行为和数据来源如何统一建模。
6. 第一版做什么、暂时不做什么，以及后续如何逐步迭代。
7. 每个版本达到什么条件才能进入下一阶段。

本文档是研发基线，不替代各业务应用自己的需求说明和详细设计。每个应用开发前仍需补充业务流程、字段、状态机、权限矩阵、接口映射和验收用例。

## 1. 执行摘要

平台定位为“企业内部轻应用与 AI 协同平台”，面向企业内部和企业 B 端场景中的自研业务应用提供统一入口、公共服务、跨应用协作、企业语义和 AI 运行治理。目标负载不是面向互联网的百万级或千万级用户；设计优先级依次是业务正确性、权限与审计、故障隔离、可恢复性、接口兼容和简单运维。业务应用默认是独立项目和独立部署单元，平台不要求其编译或运行在平台后端进程内。

总体方案采用：

- 一个统一工作入口。
- 一套通过版本化 API 和事件开放的公共平台能力。
- 多个按业务领域划分、独立开发和部署的应用项目。
- 平台事务数据、平台可重建只读投影与各应用自有数据保持逻辑隔离；默认共用一个 PostgreSQL 集群并使用独立数据库或 Schema、角色和迁移，只有合规、容量或 SLO 需要时才拆成物理实例。
- 统一的用户令牌、服务身份、API 网关、事件接入和应用注册机制。
- API、命令与业务事件驱动的跨应用协作。
- 一套连接各领域应用数据和 AI 员工的企业语义层。
- 统一的 AI 模型、知识、工具、权限、评测和审计能力。
- 平台公共服务内部初期可以采用模块化单体；业务应用从第一阶段起默认独立部署，不等待后续拆分。

必须长期坚持的核心边界是：

> 平台负责通用机制和统一治理；应用负责业务语义、业务数据、规则、状态和结果。

平台公共能力必须提供网络化契约。独立应用不得依赖平台内部类、共享 Session 表或平台数据库 Schema，也不得以复制平台代码的方式获得用户、权限、消息、文件和审计能力。

企业语义层统一描述“有哪些业务对象、对象由哪个应用拥有、对象之间如何关联、AI 可以读取和执行什么”，但不取代应用领域模型、业务数据库或工作流引擎。

为了尽快形成稳定基线，第一阶段不建设完整低代码平台、不追求覆盖所有场景、不全面微服务化，也不建设完整知识图谱。第一阶段只建设并验证平台的身份、权限、应用注册、API、通知、审计和可靠事件接入；使用业务中性的参考应用完成一致性测试，不把任何真实业务应用纳入平台交付范围。稳定对象 ID 和权威来源声明属于公开契约要求，但语义目录、SourceBinding、语义查询和 AI 运行能力不进入首批平台版本的同步依赖。

当前已交付的通知能力仅为 `IN_APP`/`LOCAL_REFERENCE` 站内测试通道，用于验证通知配置、幂等、状态查询和审计链路。`DELIVERED` 表示本地测试记录成功，不表示邮件、短信、Teams、企业微信等外部渠道已经投递；企业消息渠道必须在完成供应商选型、账号映射、失败补偿和独立验收后另行启用。

## 2. 背景与问题

当前企业正在将线下口头沟通、微信群协同和 Excel 填写逐步改造成线上业务操作。按照单个场景独立建设应用虽然能够快速响应局部需求，但会逐步产生以下问题：

- 每个应用重复建设账号、权限、流程、消息、附件和审计。
- 产品、物料、订单、工单、人员等数据被重复复制。
- 各应用状态和数据口径不一致。
- 跨部门流程被切割在多个应用中。
- 应用之间形成大量点对点接口。
- 技术栈、数据库和部署方式逐渐失控。
- 每个应用单独维护，整体研发和运维成本持续增加。
- AI 员工只能看到局部数据，无法获得完整流程上下文。

本项目需要同时满足两类诉求：

1. 业务侧要求快速上线、快速试错和持续变化。
2. 企业侧要求统一数据、统一治理、可维护和可演进。

因此，目标不是把所有应用合并为一个巨型应用，而是在保持领域应用边界和数据所有权的前提下，为内部自研应用建立统一运行底座。

## 3. 产品定位、目标与非目标

### 3.1 产品定位

产品建议命名为：

> 企业内部轻应用与 AI 协同平台

它是企业内部自研应用的协同、自动化和 AI 运行平台，不是承载所有业务语义的巨型应用。

### 3.2 产品目标

- 员工通过一个入口访问内部应用、消息和待办。
- 新场景能够复用公共能力，降低上线成本。
- 相关业务场景按照领域聚合，不再“一场景一应用”。
- 每个应用拥有清晰的数据和代码边界。
- 每个应用能够独立建库或建 Schema、构建、部署、扩缩容和回滚，并通过标准接入协议复用平台能力。
- 每个领域应用保持自身业务数据和状态的所有权。
- 用户身份、组织、角色授权、消息通知、文件、审计等公共能力通过平台 API 或事件提供，不在应用内重复建设。
- 跨应用协作统一经过公开 API、命令和业务事件。
- 形成统一的业务对象、关系、指标、知识和行为语义，减少跨应用口径差异。
- AI 员工通过语义对象获得跨应用上下文，不直接理解应用数据库表和内部实现。
- AI 员工通过受控工具参与流程，所有行为可评测、可审计。
- 形成从应用创建、开发、测试、发布到退役的完整治理机制。

### 3.3 非目标

第一阶段明确不做：

- 将所有应用业务数据合并到平台公共 Schema。
- 允许应用直接读写其他应用的数据库表或内部代码。
- 为所有需求建设万能业务模型或万能业务表。
- 一开始就建设完整的拖拽式低代码平台。
- 一开始就把平台公共服务内部拆成大量微服务；该限制不改变业务应用默认独立部署的原则。
- 一开始覆盖多个工厂和所有部门。
- 第一阶段建设原生移动端、小程序或完整移动 Web 适配。
- 允许 AI 直接连接应用数据库或绕过应用服务执行写操作。
- 第一版建设企业级数据湖、实例级知识图谱、RDF/OWL 推理系统和复杂自主 Agent。
- 用一套万能本体替代各应用的领域模型、业务表和业务责任。
- 把语义对象直接等同于 ORM 实体或数据库表结构。

## 4. 关键术语

| 术语 | 定义 |
| --- | --- |
| 平台 | 通过 API、事件和必要 SDK 提供身份、权限、流程、文件、消息、跨应用协作、AI、审计和运维等通用能力 |
| 应用 | 围绕一个相对完整业务领域建设的独立项目，默认拥有自己的前后端、部署单元和数据存储 |
| 平台接入面 | 面向独立应用提供的应用注册、用户令牌、服务身份、API 网关、事件接入、契约目录、配额和审计能力 |
| 独立应用 | 独立构建、发布和运行，只通过平台公开 API、事件或版本化 SDK 使用公共能力，不访问平台内部实现或数据库 |
| 场景 | 应用中的一个具体业务闭环；其定义和验收属于对应业务应用，不属于平台实现 |
| 数据拥有应用 | 对平台内部某类业务实例、状态、规则和写入操作拥有最终责任的领域应用；不用于虚构 ERP/MES 等外部主数据的所有权 |
| 权威来源系统 | 对某类数据提供正式记录和最终业务口径的内部应用或外部企业系统 |
| 平台访问责任应用 | 在平台内负责发布来源查询契约或只读投影，并承担认证、映射、新鲜度、降级和对账的领域应用或适配应用 |
| 平台数据 | 用户账号、组织、任务、文件元数据、审计、跨应用协作记录等通用数据 |
| 应用数据 | 由具体应用拥有的业务记录、状态、规则和处理结果 |
| 平台投影数据 | 从应用公开事件或快照契约生成、仅供门户、搜索、语义和 AI 查询的可重建只读数据，不是业务写入真相 |
| 应用对象引用 | 一个应用对其他业务对象的稳定引用，包括权威来源系统、平台访问责任应用、语义类型、对象 ID 和版本 |
| 企业语义层 | 统一描述业务对象、属性、关系、状态、指标、知识、行为、来源和版本的共享语义契约 |
| 元模型 | 规定企业语义模型中允许出现的元素、字段、引用关系和校验规则 |
| 领域语义包 | 由各业务领域分别维护并独立版本化的语义定义集合 |
| 语义对象 | 对业务概念的标准描述，不等同于某张数据库表 |
| 来源绑定 | 将语义对象和属性映射到数据拥有应用或领域适配应用公开的查询契约或只读投影，并记录权威来源、访问责任应用、映射状态和版本 |
| 语义投影 | 从数据拥有应用或外部来源适配层生成的只读对象或关系视图，用于查询、搜索和 AI 上下文，不拥有正式业务写入权 |
| 行为语义 | 对对象可执行的查询、建议或命令及其输入、条件、权限、事件和风险的描述 |
| 证据链 | 记录 AI 查询所使用的对象、来源、数据版本、结果摘要和引用，以支持追溯和复现 |
| 逻辑隔离 | 通过代码模块、Schema、权限、API 和事件划清边界 |
| 物理隔离 | 独立进程、独立数据库或独立集群 |

## 5. 产品设计原则

### 5.1 平台提供机制，应用定义业务

例如：

- 平台提供流程引擎，应用定义流程节点和分支条件。
- 平台提供规则执行能力，应用定义领域校验和审批条件。
- 平台提供消息渠道，应用决定何时通知谁。
- 平台提供 AI 模型和工具，应用定义 AI 员工的任务与权限。

### 5.2 一个场景不等于一个应用

共享核心数据、业务规则和负责人的场景，应组合成一个应用。

示例：

~~~text
领域应用 A
├── 核心业务记录
├── 补充处理场景
├── 领域报告
└── 领域复盘

领域应用 B
├── 核心业务记录
├── 协作处理场景
└── 领域查询
~~~

### 5.3 应用拥有代码、运行和数据边界

每个应用拥有独立项目、构建产物、部署单元、业务表、迁移脚本和数据责任。默认在共享 PostgreSQL 集群中使用独立逻辑数据库或专属 Schema，并始终使用独立运行角色、连接池和迁移，不得与平台公共服务共用写权限。只有合规、容量、恢复目标或故障域要求需要时才拆分物理实例；物理部署方式不改变应用的数据所有权。

### 5.4 业务数据留在拥有应用

每个领域应用维护自己拥有的业务记录、状态和规则。平台公共模块与其他应用只保存稳定引用和必要只读快照，不维护第二份可独立修改的业务数据。

### 5.5 独立应用优先，平台内部渐进拆分

业务应用从第一阶段起默认作为独立项目，通过 API 和事件接入平台。平台身份、权限、消息、文件、审计、语义等公共服务内部可以先采用模块化单体，达到独立扩容、发布、安全或团队条件后再拆成服务；平台内部采用单体不等于把业务应用合并进同一进程。

### 5.6 配置解决差异，代码承载稳定业务

表单展示、流程节点和通知模板可配置；频繁查询、参与规则、需要约束和长期维护的数据必须建正式业务表及领域模型。

### 5.7 所有高风险 AI 操作必须受控

AI 只能通过注册工具或业务 API 执行业务操作。资金支付、受监管审批、主数据关键变更和设备控制必须保留人工确认或确定性规则。

### 5.8 稳定标识前置，语义能力渐进

V0.1/V0.5 先在普通 API、事件和快照契约中建立稳定的应用 ID、对象 ID、权威来源、数据版本和负责人约定，避免数据和接口形成后再返工，但不建设语义目录或运行服务。达到第二应用复用、跨域发现、统一搜索或 AI 数据需求门禁后，再从 V1.1 按用例建立命名空间、语义包、SourceBinding 和自动校验；语义查询、跨域关系、行为执行和图推理继续按业务价值逐步上线。

### 5.9 定义层、实例层和执行层分离

- 定义层描述对象、关系、行为和规则是什么。
- 实例层保存具体业务记录；内部记录由对应领域应用拥有，外部记录仍由权威来源系统拥有并通过适配应用访问。
- 执行层由应用服务、工作流、规则、事件和跨应用协作组件完成实际操作。

语义定义不能绕过应用边界直接写实例数据，语义投影不能成为第二套可修改的业务主库。

### 5.10 每类机制只有一个执行真相

本体可以引用流程、权限、规则、补偿和质量要求，但不重复实现工作流引擎、IAM、规则引擎、Saga 协调器和监控平台。执行状态以对应的平台或应用组件为准，语义层保存稳定契约、引用和版本。

## 6. 用户与角色

| 角色 | 主要职责 |
| --- | --- |
| 普通员工 | 发起申请、处理待办、查询状态、补充资料 |
| 业务处理人 | 接收任务、审核、分派、执行和反馈 |
| 流程负责人 | 设计业务流程、定义 SLA、监控流程绩效 |
| 应用负责人 | 对应用范围、路线图、质量和运营结果负责 |
| 应用开发者 | 开发页面、业务规则、领域模型和接口 |
| 平台管理员 | 管理用户、组织、应用、公共配置、消息和运行状态 |
| 平台运行负责人 | 负责发布窗口、容量、备份恢复、告警值守、故障协调和运行手册 |
| 应用协作管理员 | 管理跨应用能力目录、服务身份、命令、事件、重试和补偿 |
| 数据负责人 | 定义数据含义、权威来源系统、平台访问责任应用、质量标准和保留策略 |
| 语义建模负责人 | 维护领域词汇、语义包、跨域关系、版本和变更影响；可由数据负责人兼任 |
| 安全审计人员 | 查看权限、敏感操作和审计记录 |
| AI 运营人员 | 管理 Agent、知识、工具、评测集和反馈 |

所有权限必须由服务端校验，前端隐藏按钮不能替代权限控制。

建设初期允许同一人员兼任多个治理角色，但每项职责必须登记主负责人、备份负责人和可投入时间。V1.0 上线前必须形成运行 RACI、告警值守安排和离岗交接清单，不得仅以“兼职”代替责任确认。

## 7. 产品能力地图

### 7.1 统一工作入口

- 平台账号登录、统一授权流程和短期用户令牌。
- 应用门户、应用搜索，以及独立应用入口和深链接跳转。
- 统一待办、已办、抄送和我发起的。
- 消息中心。
- 最近访问和收藏。
- 全局业务搜索。
- 个人工作台。

### 7.2 应用运行能力

- 应用注册与生命周期。
- 独立应用入口、回调地址、API 地址、健康检查、菜单和权限注册。
- 用户令牌验证、服务身份、应用级 scope、配额和调用审计。
- 平台公共服务 API、事件契约和版本化接入 SDK。
- 业务表单与详情页。
- 流程发起和任务处理。
- 评论、附件和业务时间线。
- 字典、编码和模板。
- 数据导入导出。
- 业务查询和轻量报表。

### 7.3 公共平台能力

- 用户和组织的独立维护、批量导入、停用及查询 API；职位名称仅作为用户展示字段。
- 权限点注册、RBAC、数据范围、授权查询和决策 API。
- 流程、任务和统一待办 API/事件。
- 文件上传授权、下载授权、元数据和对象存储 API。
- 站内消息、通知请求、企业渠道和送达回执 API/事件。
- 编码服务。
- 审计服务。
- 应用配置和功能开关。
- 搜索服务。

### 7.4 跨应用协作中心

- 应用 API、平台公共 API 和业务能力目录。
- 应用对象引用。
- 独立应用事件接入、发布和订阅。
- 幂等、重试、死信和人工补偿。
- 跨应用命令状态、调用日志和结果核对。
- 应用服务身份和最小权限。

### 7.5 企业语义中心

- 元模型、命名空间和语义 ID 管理。
- 领域语义包注册、校验、评审、发布和废弃。
- 业务对象、属性、状态、关系和指标目录。
- 来源绑定、权威来源系统、平台访问责任应用、映射状态和版本管理。
- 行为、规则、事件、知识引用和风险等级目录。
- 语义模型依赖、变更影响和引用完整性检查。
- 面向应用、搜索和 AI 的语义发现与上下文接口。
- 数据版本、结果摘要和 AI 证据链。

### 7.6 AI 员工中心

- 模型网关。
- 知识库和检索服务。
- Agent 定义。
- 工具注册和权限控制。
- 提示词、模型和知识版本。
- 人工确认。
- 运行记录和引用来源。
- 评测、反馈、成本和时延统计。

### 7.7 运营与治理

- 应用负责人和数据负责人。
- 应用版本和发布记录。
- 日志、指标、链路和告警。
- 数据字典和接口契约。
- 使用量和业务效果分析。
- 应用停用、归档和拆分管理。

持续运营责任按以下边界落实：

- 流程负责人对业务周期、超时和闭环率负责。
- 应用负责人对使用率、需求取舍、应用质量和停用决策负责。
- 平台运行负责人对平台可用性、容量、备份恢复、告警和事故复盘负责。
- 数据负责人对来源、口径、质量和 SourceBinding 验证负责。
- 应用协作管理员对跨应用契约、积压、重试、死信和人工补偿负责。
- AI 运营人员只在 AI 能力正式启用后对评测、反馈、成本和模型版本负责。

V1.0 上线前，上述角色必须形成可执行的 RACI；没有专职岗位时，应明确兼任关系、每周容量、升级路径和备份人员。

## 8. 平台与应用的边界

| 能力 | 平台负责 | 应用负责 |
| --- | --- | --- |
| 身份 | authentik 负责账号凭据、登录认证、标准授权流程、用户令牌签发与公钥发布；平台负责用户映射、组织和授权版本 | 独立应用不处理密码，在本地验证 authentik 令牌并引用稳定用户和组织 ID |
| 权限 | 权限点注册、角色授权、数据范围框架、授权查询和决策 API | 声明权限点和业务数据范围，服务端执行对象状态与业务条件校验 |
| 页面 | 门户、导航、独立应用入口、设计规范和可选前端资产包 | 独立应用拥有自己的页面、前端构建、路由和交互 |
| 表单 | 组件、渲染、版本能力 | 字段、校验和业务含义 |
| 流程 | 引擎、任务、转办、SLA 及 API/事件 | 独立应用定义节点、分支、业务状态映射和回调处理 |
| 数据 | 平台公共数据基础设施和治理规范 | 独立应用拥有自己的数据库或 Schema、业务实例、状态、规则和迁移 |
| 文件 | 上传授权、下载授权、元数据、存储和扫描 API | 独立应用维护文件用途、业务关联和必填规则 |
| 消息 | 通知请求、模板、站内信、企业渠道、送达与回执 API/事件 | 独立应用决定触发条件、接收人、模板参数和业务内容 |
| 跨应用协作 | API 网关、契约目录、服务身份、事件接入、幂等模板、重试和补偿机制 | 按启用能力发布公开契约；可靠事件生产者维护 Outbox，产生本地副作用的事件消费者维护 Inbox |
| 外部企业系统接入 | 适配器规范、凭据托管、契约注册、同步观测和访问审计 | 领域适配应用负责字段映射、权威源声明、新鲜度、降级和对账规则 |
| 语义 | 元模型、注册、校验、版本、发现和证据机制 | 定义并拥有本领域对象、关系、状态、规则、行为和来源绑定 |
| AI | 模型、知识、工具、审计和评测 | 任务、领域知识、工具实现和确认规则 |

边界判断原则：

1. 去掉任何具体领域名词后仍然成立的能力，倾向放平台。
2. 包含具体业务含义、规则、状态和最终责任的能力，放应用。
3. 只有一个应用使用且仍在快速变化的能力，先放应用。
4. 被多个独立领域稳定复用后，再抽取为平台能力。
5. 一个应用拥有的业务结果不在平台公共 Schema 或其他应用中重复维护为可写副本。
6. 平台统一语义建模机制，领域应用和数据负责人共同拥有具体语义定义。
7. 语义层只能通过应用公开接口、事件、授权查询或来源绑定获取实例数据，不能绕过应用直接写表。
8. ERP、MES、PLM 等外部系统继续作为权威数据源时，必须通过登记的领域适配应用或外部数据网关接入；SourceBinding 不直接绑定任意外部私有接口。
9. 业务应用默认且优先采用 `STANDALONE_APP` 模式，独立构建、部署和回滚；平台内部模块不伪装成业务应用，未来扩展模式需另行立项和评审。
10. 平台公共能力必须同时具备网络契约和版本策略；SDK 只是调用封装，不能要求应用链接平台内部实现。
11. 独立应用只能使用 authentik 签发且面向正确 audience 的用户令牌或服务身份调用公共能力，不能共享身份系统 Cookie、Session 表、数据库账号或内部网络信任。

独立应用通过平台接入面验证用户令牌或服务身份，并通过版本化 API 使用用户权限、流程、文件、消息、审计和语义等公共服务。应用之间通过公开 API、命令和事件协作，不经过平台数据库交换业务数据。每个应用只访问自己的数据存储；平台需要统一列表、搜索、语义或 AI 上下文时，只消费应用公开事件形成可重建只读投影，详情和权威校验仍通过应用 API 获取。

### 9.1 推荐部署形态

第一阶段采用“平台核心模块化、业务应用独立部署”的形态：

- 一个统一 Web 门户；第一阶段以桌面浏览器为正式支持终端，不包含原生移动端、小程序或移动端专项验收。
- Traefik 作为基础设施接入层，只负责 TLS、入口路由、请求大小限制和必要的基础限流；Python 平台接入模块负责令牌校验、应用身份、scope、request_id 和调用审计。只有出现明确的共享资源保护需求时才增加应用级配额，V0.1 不自研通用反向代理、API 管理或网关产品。
- 一个平台公共服务部署单元，使用 FastAPI 模块化单体按阶段启用身份映射、权限、消息、审计和应用注册等公共模块；HTTP API 与事件 Worker 使用相同模块代码但以不同进程运行。文件、流程适配、投影和语义治理按实际用例启用，不要求空模块提前形成生产依赖。
- 每个业务应用拥有独立项目、前后端构建、后端部署单元、运行配置和发布流水线；任何真实业务应用都不编译进平台公共服务后端，也不属于本平台建设计划的交付物。
- 默认使用一个 PostgreSQL 集群承载 authentik、平台和业务应用的逻辑数据库；平台核心、平台只读投影与各应用使用独立数据库或 Schema、独立角色、独立连接池和独立迁移。任何角色不得跨边界读写。只有法规隔离、恢复目标、容量或故障域要求无法通过逻辑隔离满足时，才拆分物理数据库实例。
- 当至少一个应用登记 `EVENT_PUBLISHER`、`EVENT_CONSUMER` 或 `PROJECTION_SOURCE` 时启用 RabbitMQ 和相应 Worker，按应用分配发布与订阅权限，契约进入仓库目录；只使用 `API_CLIENT` 的应用不运行事件 Worker，也不创建 Outbox/Inbox。
- authentik 保存凭据和会话并签发短期用户令牌与服务令牌；平台维护用户映射、组织、角色、权限和授权版本。应用不读取身份系统 Session 表，也不接收用户密码。
- 语义能力启用后，语义定义、版本和来源绑定使用平台 semantic Schema；业务实例数据始终保存在独立应用自己的数据存储中。V0.1 不要求部署语义运行服务。
- V0.1 不部署通用工作流引擎、统一流程端口或待办运行服务。后续只有平台产品范围明确包含统一待办，或外部应用提出经过批准的复用需求时，才建设最小待办契约；引入不依赖 JVM 的工作流产品时使用独立数据库或独立 Schema，其内部表不作为业务查询接口。
- 业务用例需要附件时才启用对象存储，数据库只保存文件元数据；没有附件需求的接入基线不强制部署对象存储。
- 基础模式先提供结构化日志、request_id、健康检查和必要指标；完整链路追踪、集中日志和告警平台按生产 SLO 接入，不长期把运行日志堆积在业务主库。
- 第一阶段不要求图数据库、搜索服务或向量数据库；出现经过验证的查询或 AI 用例后再通过 ADR 引入。

业务应用与平台进程隔离后，应用自身崩溃不应直接导致平台或其他应用进程崩溃；API 网关、身份、事件总线、消息渠道和共享数据库集群仍是公共依赖，必须通过超时、限流、配额、缓存和降级控制故障传播。

部署按能力和可用性目标分为三档：

| 档位 | 组件 | 适用条件 |
| --- | --- | --- |
| 基础接入 | Traefik、authentik、平台 API、门户、单 PostgreSQL 集群 | 应用只使用同步 API，允许按维护窗口停机 |
| 标准事件 | 基础接入组件，加 RabbitMQ、Outbox 发布器和事件消费者 | 存在可靠业务事件、异步通知或平台只读投影；本项目正式接入的推荐档位 |
| 高可用 | 无状态组件多实例、PostgreSQL 高可用或托管方案、RabbitMQ 高可用拓扑及独立恢复演练 | 业务 SLO、RPO、RTO 明确要求；不能仅因预计用户增长而默认启用 |

三种档位使用相同 API、事件和数据所有权契约。升级档位不得要求修改业务模型或跨应用访问数据库。

### 9.2 模块依赖规则

- 平台公共服务不能依赖、编译或部署任何具体业务应用代码。
- 独立应用只能依赖平台公开 API、事件契约和版本化 SDK，不能依赖平台内部实现。
- SDK 只能包含协议模型、令牌验证、客户端和通用中间件，不包含平台业务实现或共享数据库访问。
- 应用不能直接依赖另一个应用的数据库、内部代码、部署网络或共享 Session。
- 跨应用协作通过公开服务接口或领域事件。
- 应用发布自己的领域语义包，平台语义模块不能反向包含应用业务规则实现。
- 语义查询必须经过应用公开查询或受控只读投影。
- 跨应用命令和事件只依赖公开契约，不依赖对方内部实现。
- 禁止循环依赖和未登记的点对点调用。
- 平台和应用分别执行提供方与消费方契约测试，破坏性变更通过新版本和迁移窗口发布。

### 9.4 独立应用隔离与公共依赖保护

独立部署已经形成应用与平台之间的进程级故障边界，但公共接入层、身份、事件和消息仍需防止单个应用过载：

- 接入层为所有应用设置安全默认的请求大小和超时上限；出现共享资源争用后，再按 `application_id + endpoint` 增加并发、速率和配额，并保留平台紧急停用某个应用凭据的能力。
- 事件总线按应用限制发布速率、消息大小、消费并发、积压和重试，不允许一个应用无界占用公共分区或队列。
- 每个应用使用自己的数据库角色和有上限的连接池；共用数据库集群时设置连接预算、查询超时和资源指标。
- 平台公共服务内部的 Web 请求、任务和消息消费仍设置有界并发、队列、超时和拒绝策略。
- 数据库查询设置语句超时、分页上限和批量大小；长耗时分析进入只读副本或异步任务。
- 应用调用平台或其他应用时设置连接、读取和总时限，使用熔断、限流和有界退避；调用链剩余预算不得被下游重置。
- 每个应用分别监控连接、并发、队列、错误率、时延和存储配额，并支持通过功能开关暂停入口、任务和消费者。
- 平台公共 API 不可用时，应用按照业务重要性使用缓存授权快照、延迟通知、明确拒绝或等待处理，不得默认放行权限和静默丢弃操作。

独立部署不等于完全无共享故障域。身份、网关、事件总线和消息渠道的 SLA、降级方式与应用可用性目标必须共同评审；高等级应用需要独立容量或多可用区时另行设计。

### 9.5 Python 技术基线

所有自研平台服务、领域适配应用和业务应用后端统一采用以下基线：

| 类别 | 技术选择 |
| --- | --- |
| 运行时 | Python 3.14.x 标准构建；不把正确性或容量设计建立在 free-threading 上 |
| Web 与契约 | FastAPI、Uvicorn、Pydantic 2、OpenAPI 3.1、JSON Schema |
| 数据访问 | SQLAlchemy 2.x Async、psycopg 3、Alembic；单个请求或消息任务独占会话 |
| 事件 | RabbitMQ 4.2、aio-pika、CloudEvents、AsyncAPI；手动确认、发布确认、死信和有限重试 |
| 身份 | authentik 提供 OIDC/OAuth2、PKCE、客户端凭证、会话和令牌；平台提供业务授权决策 |
| 接入层 | Traefik 提供 TLS 和入口路由；Python 服务再次验证 issuer、audience、有效期和 scope |
| 工程工具 | uv、`pyproject.toml`、`uv.lock`、Ruff、Pyright strict、pytest、pytest-asyncio |
| 可观测性 | 结构化日志、健康检查、基础指标和 OpenTelemetry 上下文；统一 `trace_id`、`request_id` 和 `application_id`，集中采集按生产 SLO 启用 |

Node.js 只用于 Vue 前端构建，不运行平台或业务后端。自研服务和选定基础设施均不得引入 JVM 运行依赖；PostgreSQL、RabbitMQ、Traefik、authentik 和对象存储属于独立基础设施，不要求由 Python 实现。

FastAPI 模块本身不构成足够的领域边界。包含业务规则和持久化模型的核心模块分为 `api`、`application`、`domain` 和 `infrastructure`；简单适配器可以采用更轻的纵向结构，但仍必须通过公开接口协作。CI 使用静态导入规则阻止跨模块导入对方 ORM Model、Repository 和内部实现。平台 HTTP API 与事件 Worker 可以共享模块包，但必须使用不同进程、不同启动入口和独立并发预算。

每个 HTTP 请求或消息处理任务创建自己的 SQLAlchemy `AsyncSession`，不得跨协程共享会话。业务数据和 Outbox 使用同一个 `AsyncSession` 与数据库事务；Inbox 去重记录和本地副作用也使用同一个会话与事务。RabbitMQ 发布和数据库提交之间不使用分布式事务，以至少一次投递、幂等消费、对账和补偿闭环保证最终一致。

V0.1 不引入 Celery、Redis、Kafka、Elasticsearch、Temporal、通用 BPMN 引擎或 Python 自研网关。RabbitMQ 同时承载已登记的生产事件和必要后台任务；只有出现无法由当前设施满足的明确容量、检索或流程需求后，才通过 ADR 引入新的基础设施。

技术表中的版本号是兼容基线，不代表生产环境使用浮动镜像标签。所有生产镜像和 Python 依赖必须锁定经过集成、迁移和恢复测试的补丁版本或镜像摘要；升级先通过集成环境和回滚验证，再进入生产。

M0-08 的机器可读生产清单统一维护在 `deploy/component-lock.json`，操作规则维护在 `docs/component-upgrade-policy.md`。当前锁定 PostgreSQL 18.4、Python 3.14.7、Node.js 24.18.1 LTS、Nginx 1.30.4 stable、RabbitMQ 4.2.9 和 uv 0.9.8；第三方镜像使用精确标签和多架构 OCI index digest。Compose、Dockerfile 和环境模板不得各自维护平行版本。2026-08-12 已在 `linux/arm64` 上从两个独立的全新数据卷完成两个部署档位的迁移、健康、API、RabbitMQ 和数据库权限门禁；任何标签或摘要变化必须重新验证。

## 10. 应用模型与生命周期

### 10.1 应用基本信息

每个应用必须登记：

- 应用编码和名称。
- 接入模式；V0.1 默认且只交付 `STANDALONE_APP`。
- 接入能力集合 `integration_capabilities`；默认只有 `API_CLIENT`，按需要增加 `EVENT_PUBLISHER`、`EVENT_CONSUMER` 或 `PROJECTION_SOURCE`。
- 所属业务领域。
- 应用负责人、业务负责人和数据负责人。
- 各环境的前端 `entry_url`、允许的授权回调地址、退出回调和深链接规则。
- 各环境的 `api_base_url`、健康检查地址、版本地址和可观测性入口。
- 用户令牌 audience、应用服务身份、允许的 scope、凭据轮换和紧急停用方式。
- 菜单、权限点、角色模板和数据范围声明。
- 数据库或 Schema 标识、迁移归属和备份责任。
- 领域语义包、命名空间和数据负责人。
- 发布的语义对象、关系、指标、行为和事件。
- 发布的公开 API。
- 发布和订阅事件。
- 发布到平台的只读投影契约，包括用途、字段白名单、增量事件、全量快照接口、水位、新鲜度、保留期、数据等级和重建负责人。
- 发布和依赖的应用业务能力。
- 数据等级和保留周期。
- 服务等级目标。
- 接入 SDK 或协议版本、兼容窗口和升级负责人。
- 停用、数据导出、凭据撤销和退役策略。

### 10.2 应用生命周期

~~~text
DRAFT
→ DEVELOPING
→ TESTING
→ VALIDATING
→ PUBLISHED
→ SUSPENDED
→ RETIRED
~~~

应用项目独立发布自己的版本，并向平台登记版本、契约指纹和环境状态。只有通过令牌与权限、安全、数据、接口、事件、可观测性和回滚检查的版本才能从测试进入验证或正式发布。平台可以下架门户入口、撤销应用凭据或停止事件订阅，但不能代替应用执行数据库回滚。

### 10.3 应用运行模式

第一阶段只实现一种业务应用接入模式：

- `STANDALONE_APP`：P0、默认且优先支持。应用拥有独立项目、构建、部署、运行和数据存储，通过用户令牌、服务身份、版本化 API 和事件接入平台。

平台自身管理页面和公共服务属于平台模块，不登记为业务应用。若未来确需可插拔平台扩展，应以新的 `PLATFORM_EXTENSION` 模式单独设计安全、运行和发布边界，不在 V0.1/V0.5 范围内。所有新业务应用必须选择 `STANDALONE_APP`；已有内嵌业务代码迁移时先建立公开契约和数据边界，再独立部署，不通过共享数据库表实现过渡调用。

### 10.4 接入能力按需启用

`STANDALONE_APP` 是应用运行和治理模式，不代表每个应用必须同时使用所有集成机制。每个应用登记一个可组合的 `integration_capabilities` 集合，只对已启用能力执行对应门禁：

| 接入能力 | 适用场景 | 应用必须承担的机制 |
| --- | --- | --- |
| `API_CLIENT` | 调用用户、权限、文件、通知等平台 API | 用户令牌或服务身份、超时、错误处理和调用审计；不要求 Outbox/Inbox |
| `EVENT_PUBLISHER` | 发布不能在业务提交后丢失的生产领域事件 | 业务变化与本地 Outbox 同事务、应用侧中继、重试和发布监控 |
| `EVENT_CONSUMER` | 消费事件并产生本地持久化业务副作用 | 本地 Inbox 或等价幂等记录与业务处理同事务、重复和乱序处理 |
| `PROJECTION_SOURCE` | 向门户、搜索、语义或 AI 提供平台只读摘要 | `EVENT_PUBLISHER` 能力、字段白名单、对象版本、删除事件、带水位快照和对账；投影 Inbox 由平台维护 |

这些能力可以组合，但不能因为应用是 `STANDALONE_APP` 就全部默认启用。仅同步调用平台 API 的简单应用不建 Outbox/Inbox；只发布事件的应用不建消费 Inbox；只消费事件的应用不建发布 Outbox。普通同步通知失败可以直接反馈或按 API 契约重试；如果业务提交成功后通知绝不能丢失，则将通知请求建模为可靠事件并启用 `EVENT_PUBLISHER`。

日志、指标和链路等可丢弃遥测不属于生产领域事件，不要求进入业务 Outbox。平台提供 Integration Kit，包括迁移模板、事务内 Outbox 写入、Inbox 去重中间件、中继 Worker 或 Sidecar、事件契约代码生成和监控面板；SDK 可以减少样板代码，但对应应用仍承担自己启用能力的运行责任。

### 10.5 平台公共模块拆分条件

平台公共服务内部初期可以采用模块化单体。满足以下一个或多个条件时，再评估拆出平台服务：

- 需要独立发布且平台整体发布已成为瓶颈。
- 有显著不同的高并发或资源需求。
- 有独立容灾、可用性或安全隔离要求。
- 使用特殊技术栈或存储。
- 已有独立公共能力团队。
- 平台模块故障必须与其他公共服务隔离。
- 容量或团队边界已经超出共享运行模式。

## 11. 平台接入一致性验证

平台建设不包含任何正式业务应用。仓库中的 `examples/standalone-app` 是业务中性的接入参考应用，只用于自动化验证平台公开契约、SDK、部署和故障边界；它不是生产业务系统，不形成平台产品范围，也不能成为平台代码或数据库的反向依赖。

未来真实业务应用由各自项目另行定义需求、领域模型、状态机、字段、页面、数据责任和验收指标。平台只登记和治理其公开接入结果，不把任何具体业务应用作为 V0.1、V0.5 或 V1.0 的平台交付物。

### 11.1 验证目标

中性参考应用验证以下平台能力：

- 独立构建、部署、迁移、启动、停止和回滚。
- 应用注册、门户入口、回调白名单、健康检查和版本登记。
- authentik 授权跳转以及 OIDC Discovery/JWKS 本地令牌验证。
- 用户身份、应用级权限、授权版本与本地对象条件校验的责任边界。
- 服务身份、scope、平台 API 调用、测试通知和调用审计。
- `API_CLIENT` 默认模式不创建 Outbox/Inbox，也不运行事件 Worker。
- 按需启用 `EVENT_PUBLISHER`、`EVENT_CONSUMER` 和 `PROJECTION_SOURCE` 后的可靠事件链路。
- request_id、错误码、超时、重试、降级和独立故障边界。
- SDK、OpenAPI、AsyncAPI 及提供方/消费方契约兼容性。

工作流、表单、文件、语义和 AI 能力只在平台版本范围明确包含时使用对应的中性测试夹具，不在参考应用中虚构正式业务流程。

### 11.2 中性参考数据

参考应用只维护用于技术验证的最小记录：

~~~text
example_record
├── id
├── name
├── state
├── lock_version
├── created_at
└── updated_at
~~~

记录名称、状态和载荷不得借用真实业务含义或生产数据。`example_record` 只用于验证数据库迁移、乐观锁、权限拒绝、Outbox 原子提交、Inbox 幂等和投影重建，不能演变为通用业务表或平台正式数据模型。

### 11.3 接入验证配置

| 配置 | 必须验证的行为 |
| --- | --- |
| `API_CLIENT` | 登录、JWT 验证、权限查询、服务身份、测试通知、审计和超时；无事件表及 Worker |
| `EVENT_PUBLISHER` | 来源测试记录与本地 Outbox 同事务、发布确认、有限重试和积压恢复 |
| `EVENT_CONSUMER` | 本地 Inbox 与持久化副作用同事务、重复投递幂等和失败后重新消费 |
| `PROJECTION_SOURCE` | 字段白名单、对象版本、删除语义、快照水位、对账和从空投影重建 |

各配置必须可以独立启用和测试。不得为了让一致性测试通过而给所有业务应用默认安装全部集成机制。

### 11.4 验证参与方

- 平台产品负责人确认公共能力和错误语义。
- 平台开发者维护提供方实现和参考应用。
- 应用开发者视角的消费方测试验证接入文档与 SDK。
- 安全负责人验证身份、scope、凭据、权限拒绝和审计。
- 运维负责人验证部署、备份、恢复、告警和降级。
- 自动化测试负责覆盖重复、乱序、超时、重启和兼容升级。

不设置业务发起人、审批人或领域负责人等虚构角色；这些角色只属于未来真实业务应用。

### 11.5 外部应用与数据边界

平台不得通过参考应用预设未来业务应用的字段、角色、状态或外部系统。真实应用接入后仍遵守：

1. 应用业务库是唯一可写真相，平台不直连应用数据库同步表。
2. 应用只按已登记用途发布公开 API、事件或带水位快照；平台投影保持只读、字段最小和可重建。
3. 外部企业系统由登记的领域适配应用或数据网关接入，并声明权威来源、新鲜度、降级和对账责任。
4. 需要回写外部系统时必须使用独立命令契约、服务身份、幂等、确认和业务纠正机制。
5. 真实应用的接入问题可以推动平台改进，但不能把其领域实现合入平台模块、SDK 或公共数据库。

### 11.6 完成标准

- 参考应用可以从平台仓库中提取为独立工程，并只依赖已发布 SDK 与公开契约。
- 平台和参考应用可以分别发布和回滚，停止任一方不会导致另一方进程退出。
- 同一测试套件覆盖 API-only 和事件能力配置，且失败结果可定位到契约、版本和 request_id。
- 平台不包含任何真实业务表、业务状态机、业务页面或领域审批规则。
- 参考应用通过不代表任何真实业务应用已上线；平台产品效果需要在未来外部应用接入后另行评估，但不纳入本平台建设计划的交付范围。

## 12. 数据库设计

### 12.1 总体原则

第一阶段推荐：

> 一个 PostgreSQL 集群、多个逻辑数据库或隔离 Schema；平台公共数据、平台可重建投影和应用业务数据拥有不同角色、迁移与生命周期。

~~~text
postgres_cluster
├── authentik_db                       独立数据库和 authentik 角色
├── platform_db
│   ├── platform_core                  平台事务数据；核心迁移与运行角色
│   │   ├── application_registration   M1 实现
│   │   ├── identity / permission      M1 实现
│   │   └── notification / audit       M1 实现
│   └── platform_projection            可重建；独立迁移和写入角色
│       ├── integration_inbox
│       ├── projection_checkpoint
│       └── example_record_summary      仅用于接入一致性验证
└── standalone_app_db                  中性参考应用逻辑数据库和角色
    └── app
        ├── example_record
        ├── integration_outbox          启用 EVENT_PUBLISHER 时创建
        └── integration_inbox           启用 EVENT_CONSUMER 时创建
~~~

应用不得因为共用数据库集群而访问平台、平台投影或其他应用数据库和 Schema。共用集群是默认的运维简化方式，不改变独立项目、独立权限、独立迁移和 API/事件边界。`platform_db` 保存平台自己拥有的事务数据；其中的 `platform_projection` Schema 保存由应用数据派生、可以从事件和快照重建的只读数据，并使用独立迁移和写入角色。达到合规、容量、恢复或故障隔离阈值时，可以将任一逻辑数据库迁移到独立实例，而不改变上层契约。

### 12.2 Schema 职责

| 数据存储或 Schema | 主要内容 |
| --- | --- |
| platform_core | 平台拥有的应用注册、身份映射、组织、角色、授权版本、通知、审计和公共配置等事务数据；模块边界由代码和表命名维持，需要独立权限或生命周期时再拆分 Schema |
| workflow_ref | 业务记录与工作流实例、统一待办之间的引用；仅在平台工作流或待办能力正式立项后启用 |
| app_collaboration | 应用对象引用、契约目录、跨应用命令或 Saga 状态、调用记录、死信、补偿记录和可重建的运营投影 |
| semantic | 元模型、领域语义包、对象与关系定义、来源绑定、版本和发布记录；M5/V1.1 按明确用例启用 |
| platform_projection | 投影消费 Inbox、同步检查点、最小对象索引，以及按明确用例建设的类型化只读投影；不得保存可由平台修改的应用业务状态 |
| 独立 app_xxx 数据库或 Schema | 对应应用自己的业务表、文件关联和审计关联；启用可靠事件发布或持久化事件消费时，分别增加 integration_outbox 或 integration_inbox |
| ai | Agent、工具、运行、反馈和评测；M6/V1.2 按评测用例启用 |

### 12.3 数据所有权

| 数据 | 数据拥有方 |
| --- | --- |
| 申请、会签、评论、业务状态、业务负责人和补充附件关联 | 对应独立应用 |
| 平台流程实例引用、统一待办和消息 | 平台流程、待办与消息服务 |
| 应用业务状态和业务规则 | 对应内部应用 |
| 用户账号和组织 | 平台身份与组织模块 |
| 文件原件 | 对象存储 |
| 生产者 Outbox 记录 | 产生业务事实的应用，保存在该应用 Schema |
| 消费者 Inbox 记录 | 执行业务消费的应用，保存在该应用 Schema |
| 跨应用命令、Saga、死信和补偿状态 | 平台跨应用协作模块；不能替代应用本地原子记录 |
| 平台只读投影 | 来源应用拥有数据含义和权威版本；平台投影服务只拥有派生存储、同步检查点和重建过程 |
| 领域语义定义 | 对应应用和数据负责人；平台保存评审通过的版本 |
| 语义只读投影与关系索引 | 从数据拥有应用或外部来源适配层派生，可重建，不拥有正式写入权 |
| AI 检索与知识索引 | 平台知识与检索模块，可重建，不作为业务写入来源 |

### 12.4 业务表统一字段

核心业务表建议包含：

~~~text
id                    应用内部 UUID
business_no           人员可读业务编号
company_id             公司或法人，可选
plant_id               工厂，可选
department_id          所属或发起部门
status                 业务状态
process_instance_id    流程实例引用
owner_user_id          当前业务负责人
created_at             创建时间
created_by             创建人
updated_at             更新时间
updated_by             更新人
lock_version           乐观锁版本
data_classification    数据等级，可选
~~~

时间统一使用带时区时间类型并按 UTC 保存。人员展示时再转换为本地时区。

### 12.5 主键与业务编号

- 内部主键使用 UUID 或企业统一分布式 ID。
- 人员可读编号单独保存，例如 APP-2026-000123。
- 其他应用对象 ID 不能直接作为当前应用主键。
- 来源应用、普通对象类型和来源对象 ID 建立联合唯一约束；启用语义治理后可以额外保存语义类型，但不替代普通对象引用键。

### 12.6 应用对象引用

统一建立跨应用对象引用模型：

~~~text
application_object_ref
├── id
├── object_type
├── source_application
├── authoritative_source_system
├── source_object_id
├── source_object_code
├── source_object_version
├── snapshot_data
├── source_updated_at
├── refreshed_at
├── semantic_type                  启用语义治理后的可选扩展
└── status
~~~

引用必须能够解析到数据拥有应用或登记的领域适配应用所发布的公开查询能力。外部数据同时记录权威来源系统和平台访问责任应用。快照字段只能用于展示、搜索降级和历史依据，不能成为第二套可修改的业务数据。

参与当前应用业务约束和事务提交的引用字段或本地引用表必须保存在当前应用 Schema；`app_collaboration` 中的统一对象引用是通过协作接口维护的目录或可重建投影，不得成为当前应用业务提交成功的同步前置条件。

### 12.7 关系表与动态字段

以下数据必须建正式列或关系表：

- 经常查询、排序和统计的数据。
- 参与规则或状态流转的数据。
- 需要唯一性、非空或外键约束的数据。
- 需要跨应用共享或协作的数据。
- 需要长期维护的数据。

JSON 只用于：

- 低频扩展字段。
- 原始表单提交快照。
- 跨应用命令或查询响应的脱敏快照。
- 不参与关键规则的临时数据。

禁止使用一张通用 business_data 表保存所有应用的业务数据。

### 12.8 外键规则

- 单一应用内部使用数据库外键和约束。
- 跨项目、跨应用不直接建立强耦合写关系。
- 对平台稳定引用可保存 ID，但写入必须经过平台接口。
- 跨应用业务对象使用 application_object_ref，不直接建立跨数据库或跨 Schema 外键。

### 12.9 删除和历史

- 正式业务记录原则上不物理删除，使用 CANCELLED、VOIDED 等业务状态。
- 草稿或临时数据可以按规则删除。
- 用户可见的业务时间线与安全审计分开保存。
- 审计、事件和跨应用调用日志按时间分区并按制度归档。

### 12.10 文件、日志和分析数据

- 文件正文不保存在关系型主库，保存到对象存储。
- 数据库保存文件 ID、哈希、大小、类型、上传人、扫描状态和访问策略。
- 应用通过自己的文件关联表连接业务记录和文件。
- 日志和链路进入可观测平台。
- 大规模分析通过平台分析模块或应用只读副本完成，不在交易查询中扫描其他应用 Schema。

### 12.11 数据库权限

- 每个应用使用独立数据库角色。
- 应用角色只写自己的数据库或 Schema；启用相应事件能力时可以写本应用的 `integration_outbox` 或 `integration_inbox`。应用角色不得连接或写平台 `app_collaboration`。
- 启用 `EVENT_PUBLISHER` 的应用运行自己的 Outbox 发布器，或部署由平台提供但归该应用运行边界管理的中继组件；中继角色只能读取和更新本应用 Outbox 的投递状态。
- 会改变目标业务状态的事件消费者运行在目标应用部署单元内，使用目标应用角色，在同一事务中写目标应用 Inbox 和目标业务数据；平台只读投影消费者属于平台服务，只能写投影 Inbox、检查点和投影表。
- 跨应用协作模块使用专用角色写 `app_collaboration` 中的命令、Saga、死信、补偿和运营投影；这些记录不得作为业务事件是否原子产生的唯一依据。
- semantic Schema 由语义模块专用角色写入，领域应用通过发布接口提交语义包，不直接修改已发布定义。
- 平台投影消费者使用专用角色，只能写 `platform_projection` 中已登记的 Inbox、检查点和投影表；应用服务身份不能直接写平台投影库，平台其他服务不得通过修改投影反向改变应用业务状态。
- 平台身份、权限、消息、语义和协作运行账号不得连接或直接读写任何独立应用数据库；授权只读投影必须使用单独只读凭据、范围和审计。
- 运行账号不能是数据库超级用户或表所有者。
- 报表账号只读。
- 数据库迁移账号与应用运行账号分离。
- 生产环境禁止手工改表，所有变更进入版本化迁移脚本。

### 12.12 语义定义与实例数据存储

语义 Schema 只保存定义、绑定、版本和发布元数据，建议的逻辑实体包括：

~~~text
semantic_package
semantic_package_version
semantic_object_definition
semantic_relation_definition
semantic_metric_definition
semantic_knowledge_reference
semantic_action_definition
semantic_rule_definition
semantic_event_definition
semantic_scenario_definition
semantic_quality_annotation
semantic_source_binding
semantic_publication
semantic_validation_result
~~~

具体表结构可在详细设计阶段调整，但必须遵守以下约束：

- 语义定义使用稳定、可读、带命名空间的 `semantic_id`，例如 `domain.business_object`；业务实例继续使用拥有应用自己的主键。
- 语义定义内部版本与业务实例版本分开管理。
- SourceBinding 记录来源类型、权威来源系统、平台访问责任应用、公开查询契约或只读投影、键映射、字段映射、水位、新鲜度目标、契约指纹和验证状态。
- 来源绑定状态至少包含 `draft`、`reviewed`、`verified`、`deprecated`。
- 关系定义与实例关系投影分开存储，实例关系必须能够追溯到来源记录和生成版本。
- 语义只读投影可以保存在专用表、搜索索引或后续图存储中，但必须可重建并标记同步时间。
- 禁止建立一张承载所有业务实例的通用语义对象表，禁止通过语义 Schema 修改应用业务数据。
- 第一阶段不将图数据库列为强制依赖；只有出现稳定的多跳实例查询、关系推理或规模瓶颈后才评估引入。

### 12.13 业务应用数据进入平台的同步机制

本节只适用于登记了 `PROJECTION_SOURCE` 的应用。仅使用 `API_CLIENT` 的应用没有业务数据进入平台投影库的义务；平台需要详情时直接调用其公开查询 API。

首先区分“平台拥有的数据”和“应用拥有数据的只读投影”：

| 数据需求 | 推荐机制 | 平台落库位置 | 一致性与用途 |
| --- | --- | --- | --- |
| 用户、授权、通知请求、送达记录、平台任务和文件元数据 | 应用调用平台 API 或命令，由平台服务写自己的事务表 | `platform_db` 对应领域 Schema | 平台是该记录的拥有方，不属于业务数据同步 |
| 门户列表、统一搜索、对象目录、语义关系和 AI 上下文所需摘要 | 应用领域事件驱动增量投影 | `platform_db.platform_projection` 的已登记类型化投影或最小对象索引 | 最终一致、显示新鲜度、可从来源重建 |
| 最新详情、关键判定和写操作前校验 | 按需调用数据拥有应用的查询 API | 原则上不持久化；必要时使用有期限缓存 | 以应用实时返回为准 |
| 首次接入、历史回填或灾后重建 | 应用提供分页快照 API，或生成带清单和校验和的受控快照文件 | 投影暂存区校验后合并到正式投影 | 使用明确的 `as_of_watermark` 衔接后续增量事件 |
| 大规模分析和长期历史 | 独立数据仓库、湖仓或分析管道 | 不进入平台交易库 | 按数据治理和分析 SLA 管理 |

禁止将应用业务表定时全量复制到 `platform_db`，也禁止平台直接连接应用数据库扫描表或订阅原始数据库日志。遗留应用确实只能使用 CDC 时，CDC 连接器必须运行在应用或登记适配应用的责任边界内，把表变化转换为稳定、脱敏、版本化的领域事件后再发布；平台不能依赖来源表名和列结构。

标准增量链路如下：

~~~mermaid
sequenceDiagram
    participant S as 独立应用服务
    participant D as 应用业务库
    participant R as 应用 Outbox 中继
    participant E as 平台事件接入
    participant C as 平台投影消费者
    participant P as 平台只读投影库

    S->>D: 业务变化 + Outbox（同一事务）
    R->>D: 读取待发布 Outbox
    R->>E: 使用服务身份发布领域事件
    E-->>C: 至少一次投递
    C->>P: projection_inbox + 类型化投影（同一事务）
    C-->>E: 成功后确认
~~~

V0.1 的中性参考投影使用 `example_record_summary`，只保存验证事件、投影和深链接机制所需的字段：

~~~text
source_application_id
source_object_id
object_type
name
state
organization_id
entry_deep_link
source_version
source_updated_at
synced_at
is_tombstone
~~~

一致性测试通过 `entry_deep_link` 返回参考应用查看详情；任何未来真实应用的完整业务字段都不得因“可能以后会用”而提前复制到平台。

同步必须满足以下规则：

1. 应用在本地事务中同时提交业务变化和 Outbox，平台不参与应用事务。
2. 进入投影的事件必须携带 `event_id`、`producer_application_id`、业务对象 ID、`aggregate_version`、发生时间、契约版本和数据等级；载荷只包含投影契约批准的字段白名单，不发送数据库行镜像。
3. 平台投影消费者将 `projection_inbox` 与投影更新放在同一事务，通过 `consumer_id + event_id` 去重，并按 `source_application_id + object_type + source_object_id` 唯一定位来源对象；语义类型不是 V0.1 投影主键的前置字段。
4. 只有 `aggregate_version` 高于已保存来源版本时才更新投影；检测到版本缺口、乱序且无法自动收敛或契约不兼容时，暂停该对象更新并进入补数队列，不能用较旧事件覆盖新状态。
5. 删除、作废或隐藏通过明确的领域事件和 tombstone 状态传播；平台按来源要求停止展示并执行投影保留策略，不直接物理删除来源业务记录。
6. 平台投影是只读派生数据。任何审批、关闭、修改或高风险判断都必须回到应用 API 或命令；不得修改投影后再反向同步到应用。
7. 列表和搜索页面必须展示或能够查询 `source_updated_at`、`synced_at` 和新鲜度状态；超过 SLA 时标记“数据可能已过期”，关键操作改为实时查询或拒绝。
8. 首次全量和重建使用应用提供的快照契约，至少包含 `snapshot_id`、`schema_version`、`as_of_watermark`、记录数、校验和和分页游标或对象存储清单。平台先写暂存区并校验，再原子切换或合并；水位之后的事件继续消费，避免全量与增量之间丢数据。
9. 平台按约定周期比较事件检查点、对象数量、版本水位和抽样哈希；差异进入受审计的补数或全量重建流程。投影表必须能够在不修改应用业务库的情况下从空库重建。
10. 每个投影登记来源应用、业务用途、消费事件、快照契约、字段白名单、数据等级、授权范围、新鲜度 SLO、保留期、对账方式和运行负责人；未登记投影不得进入生产。
11. 门户、搜索、语义和 AI 只能通过平台查询服务读取投影，查询服务按当前用户、应用授权、组织和数据范围过滤；浏览器、独立应用和报表工具不得直接连接投影数据库。

第一阶段不追求“把所有应用数据同步到平台”。V0.1 只使用中性参考记录验证一个对象摘要的增量投影、快照回填、增量衔接和对账。任何真实业务投影都必须由未来外部应用按明确用途单独登记，不是平台 V0.5 或 V1.0 的默认交付物；只有被稳定用例复用或确有性能要求的数据，才考虑新增持久化投影。

## 13. 表单、流程与业务状态

### 13.1 表单策略

平台建设不包含真实业务表单。只有表单服务被正式列入平台公共能力范围时，才使用中性 Schema 验证版本、渲染、权限和校验机制；V0.1/V0.5 不建设完整拖拽式设计器。

表单定义至少包含：

- 表单编码和版本。
- 字段定义。
- 展示规则。
- 前端校验。
- 服务端校验。
- 权限和只读规则。
- 数据映射。

前端校验只改善体验，所有业务校验必须在服务端重复执行。

### 13.2 流程策略

V0.1/V0.5 不引入 Flowable、Temporal 或其他通用工作流引擎，也不提前实现空的 `WorkflowPort` 或待办运行服务。只有统一待办被明确列入平台产品范围，或多个外部应用提出稳定复用需求时，才定义最小公共契约；出现跨应用长事务、定时器、复杂补偿或大量可配置流程等明确需求，并完成无 JVM 方案 ADR 后，才引入独立工作流产品。

应用不能直接依赖具体工作流产品 API。未来接入引擎时由平台流程适配模块实现统一接口，迁移不得改变应用业务状态的所有权。

统一流程接口按版本逐步支持：

- 启动流程。
- 查询流程状态。
- 查询用户待办。
- 完成、驳回、转办和撤回。
- 任务候选人与指派。
- SLA 和超时。
- 流程变量。
- 流程事件回调。

### 13.3 业务状态与流程状态

流程引擎负责流程执行，应用负责业务状态。

错误示例：

~~~text
工作流任务完成 = 业务对象关闭
~~~

正确方式：

1. 应用命令校验业务条件。
2. 完成流程任务。
3. 应用根据结果推进业务状态。
4. 同一业务操作产生业务历史和审计记录。

## 14. API 与事件规范

### 14.1 同步与异步边界

- 查询和需要即时返回的简单命令使用 API。
- 已经发生的业务事实使用事件。
- 跨应用的长耗时命令优先异步执行。
- 不在平台与应用或两个独立应用之间实现跨数据库事务。
- 用户交互请求携带 authentik 签发的用户令牌；后台任务和应用间调用使用独立服务身份，不混用用户密码、浏览器 Cookie 或长期静态共享密钥。

### 14.2 API 基本规范

- 独立应用调用平台公共能力必须经过平台 API 网关或统一接入层；不得使用只能在平台进程内调用的内部接口作为唯一能力入口。
- 平台公共 API 与应用业务 API 分别版本化，例如 `/platform-api/v1/notifications` 和 `/api/v1/domain-records`。
- 用户请求验证短期用户令牌的签名、issuer、audience、有效期和 scope；服务调用验证应用服务身份及目标 API scope。
- 网关根据已验证凭据确定 `application_id` 和用户身份，不信任调用方自行填写的身份头。
- 浏览器回调地址和跨域来源使用应用注册表白名单；禁止通配生产来源。
- 资源命名使用业务含义，不使用万能 /form/submit 代替领域命令。
- 每个请求携带或生成 request_id。
- 创建跨应用副作用的请求支持 Idempotency-Key。
- 更新核心记录使用 lock_version 或 If-Match 防止覆盖。
- 错误返回稳定的 error_code、message、details 和 request_id。
- 分页、排序、时间和枚举格式全平台统一。
- API 契约进入 contracts/api 并参与自动化契约测试。
- 平台公共 API 声明兼容窗口、废弃日期、限额和降级语义；应用锁定 API 或 SDK 版本，不隐式跟随最新实现。

建议错误结构：

~~~json
{
  "error_code": "RESOURCE_INVALID_STATE",
  "message": "当前状态不允许执行该操作",
  "details": {
    "current_status": "INVESTIGATING"
  },
  "request_id": "..."
}
~~~

### 14.3 事件基本规范

事件应包含：

~~~text
event_id
event_type
event_version
source
producer_application_id
subject
aggregate_version
object_type
semantic_type        可选，启用语义治理后使用
semantic_version     可选，启用语义治理后使用
occurred_at
trace_id
actor
data_classification
data
~~~

其中 `event_version` 表示事件契约版本，`aggregate_version` 表示来源业务对象版本，二者不能混用。`producer_application_id` 必须与事件接入凭据匹配。生成平台投影的事件必须提供 `aggregate_version` 和稳定 `object_type`；`semantic_type` 和 `semantic_version` 是启用语义治理后的可选扩展字段，不得成为 V0.1 事件接入的前置依赖。`subject` 应保存可解析的应用对象引用，不直接暴露数据库表名。

事件类型、生产者、允许的消费者、载荷 Schema、敏感等级、保留期和兼容策略必须先登记。平台按应用身份授予最小发布和订阅权限，应用不能订阅未授权的事件通道。

事件名称示例：

~~~text
company.example.record.changed.v1
company.example.record.archived.v1
company.platform.notification.requested.v1
company.app_collaboration.command.failed.v1
~~~

事件是已经发生的事实，不使用含糊名称，例如 processDataChanged。

### 14.4 Outbox 与 Inbox

Outbox/Inbox 不是所有 `STANDALONE_APP` 的基础依赖，只在应用登记对应事件能力后启用。启用 `EVENT_PUBLISHER` 且领域事件不能在业务提交后丢失时，生产者在自己的应用 Schema 内保存 `integration_outbox`。应用业务数据与对应 Outbox 事件必须使用同一数据库连接和同一数据库事务提交；业务事务不得直接写 `app_collaboration`，也不得先提交业务数据再通过异步代码补写 Outbox。

应用项目自己的后台发布器或应用侧中继组件使用本应用数据库角色扫描 Outbox，并使用本应用服务身份异步发送事件和更新投递状态。发布器崩溃或确认丢失可能导致重复发送，因此平台承诺至少一次投递，不承诺通用的端到端 `EXACTLY_ONCE`。

启用 `EVENT_CONSUMER` 且消费会产生本地持久化副作用时，消费者在自己的应用 Schema 内保存 `integration_inbox` 或等价幂等记录，并对 `consumer_id + event_id` 建立唯一约束。Inbox 记录与消费者产生的业务状态变化必须在同一数据库事务中提交；只有 Inbox 和业务处理同时成功后才确认消息。重复事件命中唯一记录时返回既有结果，不再次产生业务副作用。

`app_collaboration` 可以保存命令或 Saga 状态、死信、人工补偿记录和可重建的运营投影，但不保存替代应用本地 Outbox/Inbox 的第二套执行真相。运营投影丢失时必须能够从本地记录和消息系统重建。

Outbox 建议状态：

~~~text
PENDING
PUBLISHING
PUBLISHED
RETRYING
FAILED
MANUAL_ACTION
~~~

Inbox 至少记录 `consumer_id`、`event_id`、`received_at`、`processed_at`、处理结果摘要和载荷哈希。业务需要重新处理时必须创建受审计的重放或纠正动作，不能删除 Inbox 记录绕过幂等。

仅使用 `API_CLIENT` 的应用不需要创建 Outbox/Inbox。启用 `EVENT_PUBLISHER` 时遵守“业务表与本地 Outbox 同库同事务”，启用会产生持久化副作用的 `EVENT_CONSUMER` 时遵守“Inbox 与本地处理同库同事务”；不引入跨数据库两阶段提交。平台可提供表结构、SDK、容器或运维模板，但中继的配置、凭据、扩缩容和失败责任属于对应应用运行边界。

## 15. 跨应用协作设计

### 15.1 协作责任

平台跨应用协作层负责：

- API 网关、用户令牌验证、应用服务身份、scope 和最小权限。
- API、命令和事件契约目录。
- 超时、重试、限流和熔断。
- 幂等和调用日志。
- 统一错误转换和命令状态。
- 接口健康监控。
- Outbox/Inbox 的表结构模板、SDK、中继镜像或部署模板、监控规范、死信和人工补偿机制。
- `app_collaboration` 中的命令或 Saga 状态、运营投影和核对能力。
- 平台只读投影的登记、消费 Inbox、版本水位、暂存回填、对账、补数、重建和新鲜度监控机制。

应用负责：

- 独立构建、部署、数据库迁移、服务身份凭据和平台 API 客户端版本。
- 发布稳定的业务查询、命令和事件契约。
- 为什么调用。
- 何时调用。
- 业务字段和业务校验。
- 按登记能力维护所需机制：可靠事件发布者维护 Outbox 和中继，产生持久化副作用的事件消费者维护 Inbox 或等价幂等记录，并保证与本地业务变化原子提交。
- 为获批的平台只读用例发布字段白名单明确的领域事件和带水位快照契约，并对来源版本、删除语义和数据正确性负责。
- 调用失败后业务处于什么状态。
- 是否允许撤回、重试或人工补偿。
- 与数据负责人共同定义语义对象、业务字段含义和来源绑定的业务正确性。

语义中心负责：

- 保存 SourceBinding、来源应用、公开契约和映射版本。
- 校验对象、属性、关系和来源引用是否完整。
- 区分 `draft`、`reviewed`、`verified` 和 `deprecated` 映射状态。
- 向 AI 和搜索提供来源透明的语义目录，不复制应用内部实现和运行权限。

### 15.2 应用业务能力接口

一个应用不应理解另一个应用或外部系统的表结构和内部服务。数据拥有应用或登记的领域适配应用通过公开契约提供稳定的业务能力，例如：

~~~text
查询领域对象
获取外部对象状态
创建领域请求
提交领域变更
关联外部业务记录
~~~

调用方只依赖业务能力契约和语义 ID。提供方调整内部领域模型或存储结构时，应保持契约兼容或发布新版本，不要求其他应用同步修改内部实现。

### 15.3 失败处理

- 目标应用暂时不可用时，按业务策略保存待执行命令或明确拒绝请求。
- 自动重试使用退避策略。
- 达到重试上限后进入人工处理队列。
- 所有命令可查询状态和最后错误。
- 提供人工重新执行和放弃能力。
- 对关键跨应用命令定期核对发起方记录与目标应用结果。

### 15.4 降级原则

- 单个独立应用的进程崩溃、内存泄漏或发布失败不得直接导致门户、平台公共服务和其他应用进程退出；门户应标记该应用不可用并保留其他入口。
- 单个应用的慢请求、事件积压或调用风暴通过网关、事件总线的应用级限流和配额隔离，达到上限时只限制该应用。
- 身份或权限服务短时不可用时，只允许使用有明确有效期和版本的已签发令牌或授权缓存；高风险写操作不得默认放行。
- 消息服务不可用时，通知请求进入有界重试或失败队列，业务提交是否继续由应用契约明确，不能静默丢失。
- 跨应用查询不可用时，页面展示明确的过期、降级或不可用状态。
- 跨应用命令不可用时，应用接受请求并显示“等待处理”，或根据业务规则明确阻止提交。
- 不允许静默丢失操作。

### 15.5 独立应用接入流程

每个应用按以下门禁接入：

1. 登记应用、负责人、环境入口、API 地址、回调地址、权限点、服务身份和数据责任。
2. 先以 `API_CLIENT` 完成基础接入；只有登记相应用途后，才申请事件发布、事件订阅或平台投影能力及其 scope、配额和数据权限。
3. 发布 API、事件、投影和语义契约，在本地替身或集成环境通过提供方与消费方契约测试。
4. 验证门户登录跳转、用户令牌、权限拒绝、服务身份、消息通知、request_id 和审计链路。
5. 验证应用自身数据库迁移；启用事件能力时再验证相应的 Outbox、Inbox、重复和乱序处理；涉及平台投影时同时验证快照水位、版本缺口、删除、对账和从空库重建。
6. 通过安全、容量、运行手册和回滚检查后进入目标环境；平台只注册和治理发布结果，不接管应用发布流水线。

## 16. 企业语义与本体建模设计

### 16.1 定位与目标

企业语义层是平台、领域应用和 AI 员工之间的共享语义契约。它需要统一回答：

- 企业中有哪些标准业务对象、属性、状态、关系和指标。
- 每个对象和字段的业务含义、权威来源系统、平台访问责任应用、数据负责人和可信状态是什么。
- 对象可以执行哪些查询、建议和命令，分别需要什么条件、权限和人工确认。
- 业务事件、规则、知识、场景和异常补偿如何与对象关联。
- AI 使用了哪个定义版本、数据版本和证据得出结论。

本项目采用轻量、工程化的本体设计：以 YAML 或 JSON 等可读元数据表达，以 Schema 和跨模型引用校验保证结构，以 API、事件或 MCP 等协议向平台、应用和 AI 提供运行能力。第一阶段不要求 RDF、OWL、SHACL、SPARQL 或图数据库。

企业语义层不是新的业务主库、工作流引擎、规则引擎或低代码平台，也不拥有任何应用业务数据的写入权。

### 16.2 分层模型

核心语义模型严格采用三层设计：

| 层次 | 主要模型 | 主要职责 |
| --- | --- | --- |
| 第一层：企业数据语义层 | Object、Property、State、Relation、Metric、SourceBinding、KnowledgeRef | 统一描述业务数据是什么、由哪个应用拥有、从哪个公开契约获得以及如何关联 |
| 第二层：业务行为语义层 | Action/Behavior、Rule、Event、PermissionRef | 描述对象能做什么、在什么条件和权限下执行，以及产生什么业务事实 |
| 第三层：业务场景编排层 | Scenario、ActorRef、WorkflowRef、Compensation、QualityAnnotation | 把多个行为编排为完整业务意图，描述参与者、主路径、异常路径、补偿和质量要求 |

版本、来源、权限、质量、证据和审计不是第四层，而是贯穿三层的横向治理能力。平台通过 Publication、DatasetVersion、BindingVersion、Evidence、Permission 和 Audit 等治理记录，对定义发布、数据读取、行为执行和场景运行进行统一追溯。

依赖方向必须保持：第三层引用第二层，第二层引用第一层；低层模型不得反向包含具体场景流程。横向治理记录三层定义及其运行时版本，但不改变三层之间的依赖方向。

### 16.3 核心元模型

#### 16.3.1 语义 ID 与命名空间

- 每个对象、关系、指标、行为、规则和事件必须拥有稳定的 `semantic_id`。
- 建议格式为 `{domain}.{concept}` 或 `{domain}.{object}.{member}`，例如 `domain.business_object`、`domain.business_object.related_object`。
- 语义 ID 使用稳定英文标识，不因中文名称、页面名称或数据库表名变化而变化。
- 语义定义 ID 与业务实例 ID 分离；业务实例继续使用内部数据拥有应用或外部权威来源系统自己的 UUID、分布式 ID 或业务主键。
- 公共概念进入 `common` 或经评审的企业命名空间；具体领域概念保留在各外部应用自己的领域命名空间。
- 已发布 ID 原则上不复用；废弃后保留重定向或替代说明。

#### 16.3.2 对象与属性

Object 至少包含：

~~~text
semantic_id
display_name
description
domain
owner_application
authoritative_source_system
data_owner
source_binding_refs
keys
properties
states
relations
actions
metrics
knowledge_refs
data_classification
version
status
~~~

Property 至少包含名称、显示名、说明、数据类型、是否必填、枚举或引用目标、是否敏感以及可选的数据质量约束。属性类型保持有限且可跨语言映射，避免在元模型中嵌入特定编程语言类型。

Object 中的 states 只描述对象业务生命周期，不保存或替代工作流任务状态。

对象定义描述业务概念，不默认生成数据库表。只有应用自己的领域设计确认需要持久化时，才映射到正式业务表。

#### 16.3.3 关系

Relation 至少包含：

~~~text
semantic_id
source_object
target_object
description
relation_type
source_cardinality
target_cardinality
direction
inverse_relation
instance_binding
owner_application
source_binding_ref
effective_time_policy
data_classification
version
~~~

关系应支持双向业务语义和实例连接规则，但不得使用语义关系直接触发跨应用级联删除。删除和失效仍由内部数据拥有应用或外部权威来源系统决定。

#### 16.3.4 指标与知识引用

Metric 至少描述指标 ID、业务定义、统计粒度、计算规则、时间口径、过滤条件、来源对象、单位、负责人和版本。同名报表字段不能替代统一指标定义。

KnowledgeRef 用于把 SOP、制度、工艺标准、案例和专家规则挂接到对象、属性、行为或场景，至少记录知识类型、稳定引用、版本、适用范围、权限和生效时间。知识正文继续保存在文档、知识库或内容系统中。

### 16.4 来源绑定与数据可信度

SourceBinding 将标准语义对象映射到数据拥有应用或登记的领域适配应用发布的查询契约或经批准的只读投影，至少包含：

~~~text
binding_id
semantic_object
source_kind              internal_application / external_system_adapter
authoritative_source_system
source_application
source_contract
source_projection        optional
key_map
field_map
relation_map
watermark
freshness_slo
fallback_policy
reconciliation_policy
contract_fingerprint
mapping_version
owner
verification_status
verified_by
verified_at
~~~

映射表达式应使用受限、可校验的语法，优先支持直接字段、应用公开查询结果内的受控关联、值映射和明确派生规则，不允许在定义中任意执行代码。SourceBinding 不允许引用其他应用或外部系统的私有表、内部类、临时地址或未发布接口。

当 `source_kind` 为 `external_system_adapter` 时，`authoritative_source_system` 和 `source_application` 均必填：前者说明业务权威源，后者说明平台内负责认证、转换、可用性、同步和对账的适配应用。SourceBinding 只能绑定适配应用发布的受治理契约或投影，不能将凭据、任意 SQL 或外部私有 URL 写入语义定义。

绑定状态采用以下规范值：

~~~text
draft → reviewed → verified → deprecated
~~~

- `draft` 可用于开发和探索，但必须向使用者显示警告。
- `reviewed` 表示技术映射已检查，业务含义仍待最终确认。
- `verified` 表示数据负责人确认可用于约定的生产场景。
- `deprecated` 表示停止新增使用，并声明替代绑定和终止日期。

AI 用于正式决策、报告或动作建议时，核心数据原则上必须来自 `verified` 绑定；例外必须显示风险并记录审批。

### 16.5 行为、规则与事件

#### 16.5.1 Action/Behavior

Action/Behavior 描述对象能够执行的最小业务能力，至少包含：

~~~text
semantic_id
owner_object
behavior_type        QUERY / PROPOSAL / COMMAND / EVENT_HANDLER
authorization_tier   LOOK / SUGGEST / ACT
input_schema
output_schema
preconditions
postconditions
applied_rules
required_permissions
produced_events
human_confirmation
risk_level
idempotency_policy
compensation_ref
tool_or_api_ref
quality_annotation
version
~~~

一个行为应尽量只表达一个清晰的业务意图。复合流程交给 Scenario 或工作流编排，不在行为内部隐式串联多个跨域步骤。

#### 16.5.2 Rule

Rule 用于可独立评审和版本化的验证、计算、推导、转换和风险规则，至少包含输入、输出、表达式或已注册规则执行组件引用、适用对象、引用行为、负责人、版本和生效时间。

以下内容不应混入通用 Rule：

- 数据库外键、非空和唯一约束，归对象或数据库设计。
- 页面展示条件，归表单或前端配置。
- 只在单个实现内部使用且没有独立业务含义的技术判断。

关键合规、质量或安全规则即使只被一个行为引用，也可以独立建模。

#### 16.5.3 Event

Event 描述已经发生的业务事实，至少包含稳定事件类型、版本、生产行为、主题对象、载荷 Schema、敏感等级和交付语义。

生产领域事件默认采用至少一次投递与幂等消费，不把端到端 `EXACTLY_ONCE` 作为通用承诺。通知类低风险事件可以使用尽力而为；关键业务事件由生产者使用 Outbox，产生持久化副作用的消费者使用 Inbox 或等价幂等机制，并配置重试和对账。

### 16.6 场景、权限、补偿与质量标注

#### 16.6.1 Scenario

Scenario 用于描述一个业务意图如何组合对象行为和事件，包含参与者、前后置条件、主路径、替代路径、异常路径、超时和对应的工作流定义引用。

Scenario 是语义和设计契约，不保存运行中的流程状态。真实业务应用的执行真相是其版本化状态机；平台待办能力正式启用后只保存公共任务契约。未来引入工作流产品时，流程实例、任务、网关和计时器以该执行组件为真相，但应用业务状态仍由应用拥有。

#### 16.6.2 ActorRef 与 PermissionRef

本体只引用平台身份与权限模块中的用户类型、角色编码、权限编码和数据范围，不复制账号、组织树和授权结果。实际授权必须由服务端权限引擎按当前用户身份实时校验。

#### 16.6.3 Compensation

写行为可以声明补偿行为、业务纠正动作、重试、退避、人工处理、死信和幂等键。并非所有业务操作都可以技术回滚；受监管审批、主数据发布等操作应建模为受审计的反向业务动作或人工纠正流程。

#### 16.6.4 QualityAnnotation

对关键行为和场景可以标注响应时间、可用性、一致性、并发策略、审计、幂等、数据新鲜度和风险等级。实际监控阈值和执行配置仍由可观测平台、网关或基础设施管理，语义层保存业务要求和引用。

### 16.7 类模型、实例和语义投影

必须明确区分三类数据：

| 类型 | 示例 | 所有者 |
| --- | --- | --- |
| 类模型 | “业务对象 A 可以关联业务对象 B” | 领域语义包 |
| 业务实例 | “对象 A-2026-001 关联对象 B-10023” | 内部记录由数据拥有应用负责；外部记录由声明的权威来源系统负责 |
| 语义投影 | 为搜索或 AI 生成的业务对象只读关系 | 语义、搜索或分析基础设施 |

语义投影必须记录来源对象、来源版本、生成时间和投影版本，可以重建，不能接受正式业务写入。跨域查询优先通过公开查询接口或按需上下文组装；只有在性能和多跳关系需求稳定后，才建设持久化实例关系图。

### 16.8 领域语义包与治理边界

建议目录或逻辑包结构：

~~~text
semantic-models/
├── common/
├── domain-a/
├── domain-b/
└── domain-c/
~~~

| 责任方 | 主要职责 |
| --- | --- |
| 平台语义中心 | 元模型、注册、校验、版本、发布、发现、证据和影响分析 |
| 领域应用团队 | 定义本领域对象、状态、关系、行为、规则和场景语义 |
| 数据负责人 | 确认业务含义、权威来源系统、平台访问责任应用、指标口径和绑定可信状态 |
| 应用协作团队 | 协调应用或适配层公开契约、字段映射、契约指纹、水位、降级、对账和调用健康；由相关应用团队共同参与 |
| IAM、工作流、规则和监控平台 | 执行权限、流程、规则和质量控制，提供稳定引用 |
| AI 平台 | 通过语义目录发现对象和工具，遵守当前用户权限并记录证据 |

跨领域定义变更需要同时经过定义拥有方和受影响领域评审。平台团队不能代替领域负责人决定业务含义。

### 16.9 生命周期、版本和发布

领域语义包生命周期建议采用：

~~~text
DRAFT → REVIEWED → VERIFIED → PUBLISHED → DEPRECATED → RETIRED
~~~

- 每次发布形成不可变的语义包快照和内容摘要。
- 对象、绑定、规则和动作可以独立版本化，但一次生产发布必须记录完整依赖集合。
- 删除语义 ID、修改键含义、改变关系基数、改变动作输入输出，或更换权威来源系统、平台访问责任应用与来源契约，属于潜在破坏性变更。
- 破坏性变更必须进行影响分析、提供迁移或兼容期，并更新 API、事件、工具、知识和评测集。
- 已发布版本不能原地修改；修正通过新版本发布。

发布前至少执行：

1. 单文件或单定义 Schema 校验。
2. 领域包内对象、引用、关系、动作和规则完整性校验。
3. 跨领域引用和循环依赖检查。
4. SourceBinding 与数据拥有应用或领域适配应用公开契约、只读投影的 Schema 校验。
5. 敏感字段、权限、动作等级和人工确认策略检查。
6. 兼容性和变更影响检查。
7. 正式消费方或生产使用所需的数据与业务负责人审核。

语义模型可以生成文档、图表、类型定义、事件常量、权限常量、接口骨架和校验器，但不能未经领域开发和测试直接生成可上线的业务规则、数据库迁移或高风险执行逻辑。

### 16.10 AI 运行契约

语义层面向 AI 至少提供以下概念能力，具体可以通过内部 API、工具协议或 MCP 实现：

~~~text
discover_objects       发现可访问对象和能力
describe_object        获取对象、属性、关系、状态和来源
query_objects          查询对象实例
query_metrics          查询统一指标
get_object_context     获取对象及授权范围内的关联上下文
propose_action         基于证据生成动作建议
execute_action         经授权和确认后调用注册业务能力
~~~

每次查询或建议至少生成：

~~~text
principal
application
session_id
query_id
semantic_version
dataset_or_object_version
binding_versions
source_references
result_digest
warnings
expires_at
~~~

动作建议只能引用当前用户、当前会话和允许有效期内的证据。执行动作时必须重新校验权限、对象版本、业务前置条件和人工确认，不能因为模型曾经读取过数据就获得持续写权限。

### 16.11 明确禁止的反模式

- 建设一份所有团队都可以随意修改的巨大本体文件。
- 把每个语义对象机械地生成一张数据库表。
- 用语义层复制 IAM、工作流、规则或监控系统的运行状态。
- 用一张通用对象表保存所有应用业务实例。
- 隐藏 `draft` 映射或过期数据，导致 AI 把不确定信息当成事实。
- 在没有稳定多跳查询需求前先建设图数据库和复杂推理平台。
- 语义定义发生变化但不升级版本、不分析影响。
- 让 AI 根据本体定义直接写数据库或调用未经注册的应用接口。

## 17. AI 员工设计

### 17.1 平台能力

- 统一模型调用。
- 模型和提示词版本。
- 企业知识检索。
- 语义对象、关系、指标、来源和行为发现。
- Agent 定义和执行。
- 工具注册与参数校验。
- 用户身份和权限透传。
- 人工确认。
- 引用来源。
- 输入输出脱敏。
- 运行记录、反馈和评测。

### 17.2 应用能力

每个应用定义：

- AI 员工的业务目标。
- 对应的领域语义包、可访问对象和允许的绑定状态。
- 可以读取的数据。
- 可以调用的工具。
- 输出格式。
- 准确性标准。
- 需要人工确认的动作。
- 出错、超时和低置信度处理方式。

### 17.3 授权等级

| 级别 | 语义等级 | 权限 | 示例 |
| --- | --- | --- | --- |
| L0 | 看（LOOK） | 检索、解释、分析 | 查找已授权的历史记录 |
| L1 | 说（SUGGEST） | 生成建议和草稿 | 生成原因分析或报告草稿 |
| L2 | 做（ACT） | 人工确认后执行 | 确认后创建任务或提交申请 |
| L3 | 做（ACT） | 限定范围自动执行 | 低风险提醒、数据检查和任务分派 |

V1.0 只开放 L0 和 L1。L2 需要完成工具权限、人工确认、幂等、业务纠正或补偿和评测后再上线。

### 17.4 数据、证据与审计

每次 AI 运行至少记录：

- 用户和应用。
- Agent、模型、提示词和知识版本。
- 输入摘要和引用资料。
- 语义包、对象、来源绑定和数据版本。
- 工具调用及结果。
- 输出。
- 人工修改。
- 最终是否采纳。
- 时延、错误和资源消耗。

敏感原文应按数据等级脱敏、加密或只保存安全引用。

AI 不得把语义目录当作数据权限目录。对象在本体中可见，不代表当前用户可以读取所有实例；每次对象查询和工具调用都必须执行当前身份、应用、工厂、部门和对象范围校验。

## 18. 身份、权限、安全与审计

### 18.1 身份

#### 18.1.1 authentik 与平台身份边界

- authentik 是唯一的凭据、登录流程、MFA、会话、OIDC/OAuth2 客户端、签名密钥和令牌撤销执行真相；平台不得再建设密码表、Session 表或自有令牌签发器。
- 平台维护稳定的内部 `user_id`、authentik `subject` 映射、用户业务档案、组织关系、角色、数据范围和授权版本。authentik 中的组或 scope 只用于登录与粗粒度接入，不能替代平台业务 RBAC。
- 浏览器应用使用 Authorization Code + PKCE；能够安全保存客户端凭据的独立应用后端优先采用 BFF，由后端处理授权码与令牌，浏览器只持有安全会话 Cookie。
- 后台任务和无用户参与的调用使用 authentik Client Credentials。服务令牌与用户令牌具有不同 audience、scope、有效期和审计主体，不能相互冒用。
- 每个 Python API 都通过 OIDC Discovery/JWKS 在本地验证签名、issuer、audience、有效期和 scope；不得只信任 Traefik 注入的身份头，也不得共享 authentik 的 Cookie 或内部数据库。Discovery 元数据和 JWKS 使用有界本地缓存，正常请求不得逐次访问 authentik；遇到未知 `kid` 时最多立即刷新一次，刷新失败且本地没有可用密钥时失败关闭。
- 用户停用、会话撤销、客户端凭据轮换和签名密钥轮换由 authentik 执行；平台监听或轮询必要变更，递增授权版本并使权限缓存失效。
- 平台用户管理 API 只能通过受限的 authentik 管理接口执行账号创建、停用和重置，不直接写 authentik 数据库；操作必须形成平台审计。
- 组织由平台维护；调整用户组织后，由平台重新计算数据范围。职位名称是用户档案中的可选文本，不直接产生任何权限。
- 不允许用户自行注册。是否与上游企业 IdP、LDAP/AD 或其他身份源联邦是独立部署配置，不改变平台依赖标准 OIDC 的应用契约。

平台侧最小数据结构：

| 表 | 用途 |
| --- | --- |
| `identity_user` | 内部 `user_id`、authentik `subject`、姓名、工号、职位名称、状态和主组织 |
| `identity_organization` | 公司、工厂、部门等组织树 |
| `identity_client_binding` | `application_id` 与 OIDC client、issuer、audience、scope 和服务身份的映射 |
| `identity_authorization_version` | 用户、组织或应用授权版本及缓存失效水位 |
| `identity_lifecycle_event` | 账号、组织和身份绑定变化的处理状态与审计引用 |

平台数据库不得出现 `identity_credential`、`identity_session`、`identity_signing_key` 或平台自签令牌撤销表。应用只保存稳定的 `user_id`、`organization_id` 和必要显示快照，不保存登录凭据。角色是唯一授权载体，职位名称不得直接绑定权限点。

V0.5 前必须指定账号生命周期负责人，定义入职、转岗、离职和紧急停用 SLA，并验证 authentik 账号状态、平台用户映射、组织角色和在途任务之间的一致性。身份变更同步失败必须进入重试、待办和审计，不允许静默保留旧授权。

#### 18.1.2 账号、组织与角色变更

身份授权变化和存量业务责任必须分开处理：

- 用户停用、角色撤销或组织调整后，登录、会话、功能权限和按当前组织计算的数据范围立即按新状态生效，不允许用历史待办作为继续保留广泛数据权限的理由。
- 历史业务记录、审批意见和审计继续保存原 `user_id`、当时组织及必要显示快照，不因人员变化重写历史事实。
- 组织、角色或账号状态变化时，平台生成影响清单，列出未完成待办、当前业务负责人、SLA、代理关系和需要对象级授权的在途记录。
- 对仍在职的组织调整，流程负责人按业务规则选择保留原明确指派、转派或增加临时对象级访问；临时访问必须有范围、原因、审批人和到期时间。
- 对用户停用或离职，不允许保留登录访问，未完成待办和负责人记录必须进入强制转派队列，由流程负责人或备份人员在约定 SLA 内处理。
- 所有自动或人工转派、临时授权和未按期处理的例外均记录审计并产生告警，确保不存在无人负责的在途流程。

### 18.2 权限

采用 RBAC 加数据范围：

- 功能权限：能否创建、查看、分派、审核、关闭。
- 数据范围：本人、部门、工厂、公司或指定对象。
- 业务条件：例如只有业务对象负责人才能执行特定状态变更；该条件由应用服务端校验。
- 独立应用通过注册 API 发布带应用命名空间的权限点和可选角色模板，例如 `example.record.update`；平台负责角色授权、组织范围和权限版本，不能由应用自行伪造平台授权。
- 用户令牌只携带稳定身份、应用 audience、粗粒度 scope 和权限版本。应用通过授权查询或决策 API 获取当前权限与数据范围，并在自己的服务端执行对象归属、当前状态和业务条件校验。
- 独立应用不得在每个普通业务请求中无条件同步调用平台权限 API。应用级授权结果使用带版本和有效期的本地缓存；对象归属、记录状态、流程节点和其他领域条件始终在应用本地计算。确需在线决策的高风险操作必须显式登记，并定义平台不可用时的失败关闭行为。
- 只读低风险请求可以在约定时限内使用签名令牌或版本化授权缓存；高风险写操作在缓存过期、用户停用或授权服务明确不可用时默认拒绝，不得默认放行。
- 平台权限 API 返回授权依据和版本，独立应用的业务审计同时记录授权版本、命中的权限点和对象条件结果。
- 角色按系统责任命名，例如“记录处理人”“记录负责人”，不得把用户档案中的职位名称直接当作授权角色。
- 职位名称变化不自动授予或撤销角色；角色调整必须经过明确授权并记录审计。

权限编码示例：

~~~text
example.record.create
example.record.read
example.record.update
example.record.archive
~~~

### 18.3 审计

关键操作必须记录：

- request_id。
- 操作用户和代理身份。
- 应用和业务对象。
- 操作类型。
- 操作时间。
- 操作前后关键值。
- 来源 IP 或终端信息。
- 成功或失败。

审计记录原则上追加写，不允许普通应用账号修改。

### 18.4 安全要求

- 所有传输使用加密通道。
- 密钥和接口凭据进入密钥管理服务，不写入代码或普通配置。
- 文件上传校验类型、大小和恶意内容。
- 敏感日志和错误信息脱敏。
- 前后端执行统一输入校验。
- 依赖和镜像执行漏洞扫描。
- AI 和普通用户均遵守最小权限。

## 19. 非功能需求

以下为初始建议，正式数值需由企业 IT、安全和业务共同确认。

### 19.1 可用性

- 可用性档位由业务中断影响、RPO 和 RTO 决定，不根据注册用户数或预估并发量自动升级为高可用架构。
- V0.5 内部验证环境允许计划内维护。
- V1.0 平台公共接入面和核心公共服务在约定服务窗口内的月度可用性目标建议不低于 99.5%；每个独立应用另行登记自己的 SLO。
- 独立应用进程故障不得直接终止平台和其他应用进程；门户、网关和事件总线应只隔离或标记故障应用。
- 身份、权限、网关、事件和消息属于共享公共依赖。平台必须公布各能力的 SLO、超时和降级语义，应用必须将这些依赖纳入自身可用性预算。
- 共用数据库集群时仍存在基础设施共同故障域；要求更高隔离等级的应用使用独立数据库实例、容量和恢复策略。

### 19.2 性能

- 普通查询和保存接口，排除跨应用调用及 AI 调用后，P95 建议小于 2 秒。
- 列表默认分页，禁止无界查询。
- 跨应用和 AI 长耗时操作采用异步任务。
- 每个入口定义端到端超时预算；数据库语句、跨应用连接、读取和异步任务超时不得超过剩余预算。
- 性能测试必须覆盖单应用慢查询、队列积压和重试风暴，验证 9.4 的并发、队列和连接上限生效。

### 19.3 容量

- 所有大表按实际查询设计索引。
- 审计、事件、消息、语义投影和 AI 运行记录支持分区及归档。
- 文件不进入关系型数据库。
- 每个应用在自身运行环境配置数据库连接、Web 并发、任务并发和队列长度，并在平台网关、事件、消息和文件服务配置独立调用与存储配额。
- 达到上限时应限流、排队或明确拒绝，不得通过无界扩容把压力转移到共享数据库和进程内存。

### 19.4 备份与恢复

- 生产数据库开启持续备份或时间点恢复能力。
- 对象存储启用版本或备份策略。
- 定期执行恢复演练。
- 初始建议 RPO 不高于 15 分钟、RTO 不高于 4 小时，最终以业务影响分析为准。

### 19.5 可观测性

- 所有请求贯穿 request_id 和 trace_id。
- 日志至少包含应用、模块、用户、业务对象和错误码。
- 按应用监控接口成功率、时延、数据库连接或查询并发、执行队列、事件积压、跨应用调用、任务失败和配额使用率。
- 平台和各独立应用分别监控进程堆、CPU、线程或事件循环、连接池和数据库健康度，并通过 application_id、request_id 和 trace_id 关联跨项目链路。
- 监控用户令牌失败、服务身份调用、scope 拒绝、凭据过期、事件授权失败和单应用配额触顶。
- 监控每个投影的事件消费延迟、来源版本水位、版本缺口、快照进度、对账差异、死信、最后成功同步时间和从空库重建结果。
- 监控语义包发布、来源绑定验证、投影新鲜度、悬空引用和上下文查询失败。
- 告警必须关联处理责任人和运行手册。

### 19.6 正式支持终端

- V0.5 和 V1.0 正式支持企业桌面浏览器中的 Web 门户，支持范围、最低版本和分辨率由启动前技术选型确认。
- 第一阶段不交付原生移动应用、小程序或移动端专项适配，不把架构图中的未来入口计入验收范围。
- 如果平台正式范围需要在手机浏览器使用，应单独冻结最小响应式页面、设备范围、身份认证和性能验收标准，并相应调整排期。

## 20. 开发、测试与发布规范

### 20.1 Python 工程基线

- 平台仓库使用 uv workspace、`pyproject.toml` 和提交到版本库的 `uv.lock`；真正独立的业务应用仓库拥有自己的 `pyproject.toml` 和 `uv.lock`，不得依赖平台源码路径完成构建。
- 所有 Python 代码通过 Ruff 格式与静态检查、Pyright strict 类型检查和 pytest；不能以 Pydantic 运行时校验替代静态类型检查。
- HTTP API、事件消费者、Outbox 发布器和定时任务分别提供启动入口，不在 Web 请求进程内启动无界后台线程或不可控的常驻协程。
- 外部网络、数据库和 RabbitMQ 调用必须设置连接、读取、执行和总超时；重试只能用于声明为幂等或具有幂等键的操作，并使用有上限的退避。
- SQLAlchemy `AsyncSession` 按请求或消息任务创建，禁止全局复用或在 `asyncio.gather()` 的多个任务之间共享。
- Alembic 是唯一数据库结构迁移入口，不在生产启动时调用 ORM 自动建表。
- Node.js 依赖只存在于 Vue 前端工程，不出现在后端容器和 Worker 运行镜像中。

### 20.2 环境

环境按逻辑职责隔离，不要求长期维护四套等规模基础设施：

- 开发：开发者本地或按分支临时环境，用于快速调试，不作为共享验收基线。
- 集成测试：从 V0.1 建立的共享稳定环境，用于自动化集成、迁移、契约和端到端测试；不得与个人开发环境混用。
- 用户验收：V0.5 平台验收前按需创建或启用，使用受控初始化数据，由平台管理员、应用开发者、安全和运维角色验证；可以按版本窗口启停，但与正在变化的集成测试环境逻辑隔离。
- 生产：首次正式提供平台服务前建立。V1.0 完成标准化监控、备份恢复、灰度和发布治理；生产不得与测试或 UAT 共用数据和凭据。

逻辑隔离可以通过独立账号、命名空间、数据库、Schema、队列和凭据实现，具体形态由部署平台决定。不得为节省环境而合并生产与非生产；优先使用临时开发环境、共享集成环境和按需 UAT 控制维护对象数量。

测试环境不得直接使用未脱敏的生产数据。

每个独立应用在各环境使用不同的 application_id、回调地址、服务凭据、API 配额和事件权限。集成环境提供平台 API 沙箱、签名公钥、事件主题或队列、消息测试通道和本地替身，应用不得使用生产凭据进行测试。

### 20.3 数据库迁移

- 所有建表、索引和数据修复进入迁移脚本。
- 平台迁移脚本由平台团队维护；应用数据库迁移由对应独立应用团队维护并随应用版本发布。
- 使用先扩展、迁移、再收缩的兼容策略。
- 发布失败必须有回滚或前向修复方案。

### 20.4 测试层级

- 领域规则单元测试。
- 应用用例测试。
- 模块边界测试。
- 数据库迁移测试。
- API 契约测试。
- 事件契约测试。
- 用户授权跳转、令牌签名与 audience、服务身份、scope、凭据撤销和跨域回调测试。
- 平台公共 API 的提供方契约测试，以及独立应用的消费方契约测试。
- 语义定义 Schema、跨引用和兼容性测试。
- SourceBinding 与数据拥有应用或领域适配应用公开契约、只读投影的 Schema 测试。
- 跨应用查询、命令、事件、幂等、重试和补偿集成测试。
- 权限和数据范围测试。
- 核心流程端到端测试。
- 性能、安全和恢复测试。

### 20.5 发布

- 每次发布关联需求、变更、迁移和回滚说明。
- 平台和独立应用分别发布；应用发布不得要求重启平台，平台兼容升级不得强制所有应用同日发布。
- 应用上线前向平台登记版本、入口、API、健康检查、契约指纹和 SDK 版本，发布失败时平台可回退入口或撤销新凭据。
- 使用功能开关控制未完全开放的能力。
- 内部验证用户和正式用户分批放量。
- 高风险变更执行灰度发布。
- 生产问题必须能够定位到版本、请求和业务对象。
- 语义包发布必须生成不可变版本、内容摘要、校验结果和变更影响说明。
- 应用、API、事件或工具依赖的语义破坏性变更必须先提供兼容版本或迁移方案。

## 21. 版本优先级与实施计划

### 21.1 计划假设

本路线不以固定团队规模、固定周数或互联网用户规模作为架构前提，按技术依赖、业务价值和可验证退出条件推进。人员和环境投入只影响日历时间，不改变数据所有权、安全、契约和恢复门禁。

计划基于以下适用场景：

- 面向企业内部和企业 B 端应用，用户量和并发量有限，但要求性能稳定、权限清晰、操作可审计、故障可恢复。
- `STANDALONE_APP` 是首要接入模式；平台公共服务采用模块化单体，业务应用保持独立项目、部署和数据责任。
- 同步查询和即时命令优先使用 API；已经提交的业务事实、不可丢通知和跨系统异步协作使用 RabbitMQ 事件。
- 默认使用一个 PostgreSQL 集群和隔离的逻辑数据库或 Schema；物理拆分和高可用由 SLO、RPO、RTO、合规与容量触发。
- V0.1 验证身份、权限、API、最小通知和一条可靠事件链路；语义运行能力、AI、通用流程引擎、搜索和高级治理不进入该阶段退出条件。
- 每个阶段都必须能独立部署、回滚和验收；不得以临时身份票据、共享数据库权限、跳过契约测试或删除恢复验证来维持名义进度。

本节描述版本路线；具体任务、依赖、产物、验证方式和实施顺序见[独立实施计划](implementation-plan.md)。

### 21.2 优先级定义

| 优先级 | 定义 |
| --- | --- |
| P0 | 没有它不能形成可上线闭环，或会造成难以逆转的数据、接口和安全返工 |
| P1 | 正式推广前应具备 |
| P2 | 提升复用、效率和 AI 能力 |
| P3 | 规模化和高级治理能力 |

### 21.3 V0.1：研发基础版

实施方式：完成“部署基线、身份与 API、可靠事件”三个顺序门禁后验收，不设固定周数。

目标：形成可持续开发和简单部署的平台接入骨架，并证明一个不在平台进程内的示例应用可以安全使用用户权限、消息和事件能力；不对全公司开放。

P0 范围：

- 平台公共服务模块化单体骨架和统一 API 接入层。
- Web 门户骨架，以及 `STANDALONE_APP` 应用入口、回调地址和健康状态注册。
- 独立示例应用项目，拥有自己的前端或最小页面、后端、数据库迁移和部署流水线。
- 本地或临时开发环境、共享集成测试环境和自动构建。
- 一个 PostgreSQL 集群内初始化 authentik、平台和示例应用的逻辑数据库或隔离 Schema；使用独立角色、连接池和迁移，平台投影使用平台数据库内的独立 Schema 与写入角色。
- authentik 账号登录、平台用户映射与组织维护、标准授权跳转、短期用户令牌、OIDC Discovery/JWKS 本地缓存和会话撤销最小链路。
- 应用服务身份、scope、凭据轮换占位和最小调用审计。
- 用户、组织、权限点注册、当前用户授权查询 API，以及版本化短时授权缓存约定；应用在本地执行对象级和业务条件校验。
- 站内消息或测试通知请求 API，以及一个可观察的送达结果。
- 事件契约登记、应用级发布订阅权限，以及一个示例事件从应用 Outbox 发布、被平台消费并生成对象摘要投影的最小链路。
- 平台只读投影 Schema、`projection_inbox`、来源版本水位和类型化示例投影骨架。
- 平台 API/事件契约、最小接入 SDK 或客户端示例和本地替身。
- 统一错误码、request_id、日志和审计骨架。
- 稳定的 `application_id`、业务对象 ID、权威来源和契约版本命名约定；不建设语义运行 Schema、SourceBinding 或语义查询服务。
- 业务中性参考应用骨架放在 `examples/standalone-app`，不进入平台 modules 或平台数据库迁移目录，也不承载真实领域功能。

退出条件：

- 平台和示例应用可以分别自动构建、测试和部署到集成环境；发布其中一个不要求重启另一个。
- 示例应用从门户完成授权跳转，在本地使用缓存的 JWKS 验证用户令牌后调用当前用户与权限 API，不共享 Cookie、Session 表或平台数据库账号；正常请求不逐次访问 authentik。
- 示例应用使用服务身份请求一次测试通知，并通过本地 Outbox 发布一个已登记事件；平台投影 Worker 经 Inbox 幂等消费该事件。无 scope 或凭据撤销时，API 请求或事件连接按对应契约被拒绝并留有审计或诊断记录。
- 示例事件能够幂等更新一条平台只读对象摘要投影，重复投递不会生成重复记录，平台不能通过修改该投影改变示例应用业务状态。
- 单 PostgreSQL 集群可以从空环境初始化全部逻辑数据库、角色和 Schema；平台、平台投影与示例应用的迁移可以分别执行且不会获得跨边界写权限。
- 契约测试证明平台提供方和示例应用消费方对 API、事件版本理解一致。
- 登录后可以看到按权限展示的独立应用入口，应用不可用时门户仍可使用并展示明确状态。
- 已验证错误 issuer、错误 audience、过期令牌、未知 `kid`、authentik 短时不可用、授权缓存过期、重复事件和消费者重启场景。

明确不做：

- 可视化流程设计器。
- 通用表单拖拽设计器。
- AI。
- 语义元模型、语义运行 Schema、SourceBinding、语义查询、实例图、行为执行和图数据库；稳定 ID 与来源声明只是普通契约约定，不构成语义平台。
- 对象存储、集中日志或完整链路追踪；只有本阶段用例或生产 SLO 明确需要时才启用。
- 完整的跨应用命令状态、自动补偿、死信运营和大规模事件治理；V0.1 只验证最小事件接入链路。

### 21.4 V0.5：平台公共能力版

启动条件：V0.1 的部署、身份/API 与可靠事件门禁全部通过；按平台能力和一致性验收推进，不设固定周数。

目标：让平台管理员能够配置和治理公共能力，让应用开发者只依赖公开契约与 SDK 完成接入；本版本不交付任何真实业务应用。

P0 范围：

- 平台门户、应用中心和开发者入口。
- 用户映射、组织、角色、权限点、数据范围、授权版本和访问复核管理。
- 应用注册、环境入口、回调白名单、健康检查、版本、能力集合、服务身份、scope、凭据轮换和紧急停用。
- 当前用户、授权查询与决策 API，以及授权缓存、失败关闭和对象级权限责任约定。
- 通知请求 API、测试送达通道、状态查询和调用审计。
- API 与事件契约目录、SDK、错误码、request_id、结构化日志和本地替身。
- RabbitMQ 应用级发布订阅权限，以及中性参考应用的 Outbox、Inbox、最小投影、快照水位、对账和从空 Schema 重建。
- API-only 与标准事件两套一致性测试配置；API-only 配置不安装事件表或 Worker。
- 平台管理操作审计、身份和权限拒绝审计、服务身份调用审计。
- 账号生命周期、人工名册核对和授权缓存失效的最小运行规则。
- 平台使用说明、应用接入指南、SDK 示例、故障处理和问题反馈入口。

以下能力只有正式进入平台产品范围后才实施，不作为 V0.5 退出条件：

- 文件与对象存储。
- 统一待办或工作流运行服务。
- 企业消息渠道。
- 通用表单、搜索、语义运行和 AI 能力。

退出条件：

- 平台管理员能够通过管理端完成用户、组织、角色、权限点、应用、回调、scope 和凭据生命周期配置。
- 中性参考应用可以从平台仓库提取后独立构建、迁移、部署、停止和回滚，并只依赖公开 SDK 与契约。
- API-only 配置完成登录、权限、服务身份、测试通知和审计；标准事件配置完成重复、失败、重启、积压和投影重建验收。
- 撤销参考应用凭据后，其 API 和事件调用立即按约定被拒绝并形成审计；停止参考应用不会导致平台进程退出。
- 平台数据库中不存在任何真实业务表、业务状态机、业务页面或领域审批规则。
- 所有公开 API 和事件通过提供方、SDK 和参考应用消费方契约测试。
- 已形成 V1.0 的生产加固问题清单、SLO/RPO/RTO 候选值和运行责任清单。

### 21.5 V1.0：正式生产版

启动条件：V0.5 平台公共能力与一致性测试通过，并完成生产 SLO、RPO、RTO 和运行责任确认。

目标：将平台公共接入面提升到可正式运行的生产质量，完成身份、权限、API、通知、事件、审计和运维治理。真实业务应用的开发和上线不属于本版本交付范围，正式 AI 能力也不作为本版本目标。

P0 与 P1 范围：

- 平台账号安全策略、用户批量维护、会话治理、人工名册核对、账号生命周期 SLA 和权限复核。
- 完整权限矩阵和数据范围。
- 组织、角色和账号变化后的授权失效、平台侧影响清单、临时访问和审计；业务对象与在途任务处理由未来应用自行负责。
- 统一消息渠道至少接入一种企业常用渠道。
- 公开查询、命令和事件的通用登记、身份、幂等、状态与错误契约，以及对应中性一致性测试。
- 用户令牌签名轮换、服务凭据轮换、scope 复核、单应用紧急停用和退出传播。
- 平台 API 兼容窗口、SDK 版本策略、应用级限流配额和消费方契约治理。
- 在参考应用 Outbox/Inbox 和平台事件接入基础上补齐自动重试、死信、受审计重放、人工处置入口和运营监控；真实应用仍拥有自己的本地可靠性记录。
- 使用中性参考投影补齐版本缺口检测、快照回填、增量水位衔接、周期对账、补数、删除传播和从空 Schema 重建演练。
- 跨应用命令状态、错误和结果核对页面。
- 数据备份、恢复、监控和告警。
- 已启用文件能力时完成文件安全校验；未启用时不部署对象存储。
- 平台与独立应用数据库权限隔离，以及共用集群情况下的连接与容量隔离。
- 发布、灰度和回滚机制。
- 9.4 的连接、并发、队列、查询超时、熔断和应用级配额，并完成单应用慢查询或积压演练。
- 核心 API、事件、快照和参考投影能够追溯到契约版本、来源、数据版本和负责人。
- 平台运营看板：认证、授权、API、通知、事件、投影、审计、发布和资源使用情况。
- 上线运行 RACI、告警值守、备份人员、升级路径和运行手册。

可选但不计入 V1.0 退出条件：在隔离数据和功能开关下验证一个 AI L0/L1 用例。模型网关、知识检索、AI 引用和正式业务放量统一在 V1.2 验收。

退出条件：

- 完成安全、性能、备份恢复以及平台管理员和应用开发者视角的验收。
- 参考应用记录与本地 Outbox 原子提交，参考消费者 Inbox 与本地副作用原子提交；重复事件和命令不会产生重复结果。
- 中性参考投影已完成快照与增量衔接、版本缺口和对账演练，并能够从空 Schema 恢复到约定水位；平台投影不可用于修改来源记录。
- 关键告警有责任人和处理手册。
- 单应用崩溃、慢调用、事件积压、凭据泄露模拟和下游不可用演练证明进程边界、限额、撤销与降级生效；同时明确网关、身份、事件和共享基础设施仍是公共依赖。
- OIDC 密钥、服务凭据、数据库凭据和消息凭据轮换均完成演练。
- 平台 API、事件和 SDK 的兼容窗口以及升级、废弃和回滚过程通过测试。
- 运行 RACI、值守、升级和交接安排已由相应负责人确认。
- 平台代码、数据库、管理页面和发布制品不包含任何真实业务应用的领域实现。

### 21.6 V1.1：多消费方治理版

启动条件：V1.0 稳定运行，已有多个独立消费配置或外部应用接入计划需要统一治理；语义治理只在跨应用数据发现或 AI 用例已经明确时启动。外部应用本身不属于本版本交付物。

目标：证明平台契约、SDK、管理能力和运行隔离可以低成本支撑多个独立应用，而不包含任何特定领域规则。

P1 范围：

- 应用注册、菜单、权限和配置标准化。
- 多套独立消费配置和认证测试，不复制或链接平台内部代码。
- 可复用的无业务状态组件和接入页面模板。
- 流程定义版本管理。
- 消息模板。
- API 和事件目录。
- 外部领域语义包的注册、评审、发布、废弃和变更影响分析；领域内容由外部数据负责人维护。
- 通用语义对象选择器和上下文查询契约。
- 通用应用对象选择器。
- 字典和编号管理。
- 应用级配额、指标和负责人。
- 开发脚手架和示例应用。
- SDK 多版本兼容、升级指南和独立应用认证测试套件。

退出条件：

- 至少两套相互独立的消费配置通过身份、权限、API、事件、配额和故障隔离认证测试。
- 平台核心代码不包含任何消费方业务规则，SDK 不包含领域实现。
- 外部领域可以独立维护语义包，跨域引用通过评审且没有直接数据库依赖。
- 新消费方能够在不修改平台代码的情况下登记、验证、发布和撤销自身配置。
- 公共能力复用、接入周期和兼容升级达到项目约定目标。

### 21.7 V1.2：AI 增强版

启动条件：至少一个低风险、高频、可评测的 AI 用例已确认，所需数据契约、权限、来源和评测负责人已就绪。

目标：上线第一批可评测、可追溯的 L0/L1 AI 辅助，并在证据充分后让 AI 升级为受控的 L2 业务助手。

P2 范围：

- 模型网关、模型访问策略和敏感信息控制。
- 统一知识库和知识权限。
- 知识检索、引用、语义版本、数据版本和来源证据。
- Agent、工具和提示词版本管理。
- 领域评测集。
- Action/Behavior、Rule 和 Event 的可执行语义定义。
- 关键 AI 动作的输入输出、前后置条件、权限、确认、幂等和工具映射。
- 高风险跨应用动作的补偿或业务纠正定义及质量标注。
- 必要场景的 Scenario 语义与工作流定义引用。
- AI 建议采纳率和人工修改率。
- L2 人工确认后执行。
- 工具幂等、权限和失败处理。
- 成本、时延、模型质量和安全监控。
- 按正式评测用例登记的领域 AI 助手；其领域内容由外部应用或数据负责人提供。

退出条件：

- 每个 AI 用例有离线评测和线上业务指标。
- 工具调用继承当前用户权限。
- 动作执行前会重新校验对象版本、业务条件、权限和人工确认。
- 关键动作具备人工确认、审计和幂等。
- 可以按 Agent、模型和版本回溯结果。

### 21.8 V2.0：规模化平台版

启动条件：根据实际复用结果、业务复杂度和运行指标启动，不设固定月份。

P3 范围：

- 多公司、多工厂的完整数据隔离。
- 可视化表单和流程设计能力。
- 规则配置中心。
- 应用市场或模板中心。
- 更完整的数据目录和血缘。
- 根据已验证的多跳查询需求建设实例关系索引或图存储。
- 按应用间语义互操作需要提供 JSON-LD、RDF/OWL 等导出，不将其设为内部运行前提。
- 平台容量隔离与独立扩缩容。
- 高价值模块服务化或数据库拆分。
- 原生移动端、小程序或完整移动 Web 适配，仅按已验证业务需求启动。
- L3 低风险自动执行。
- 应用成本、价值和退役治理。

启动前提：

- 已有至少两到三套独立消费方配置通过平台认证，或已有同等数量的外部应用稳定消费平台能力。
- 已明确哪些变化是通用需求，哪些属于领域特性。
- 平台团队具备持续运营能力。

### 21.9 里程碑与能力门禁

实施顺序由前置能力和验收结果驱动。日历计划可以在项目启动时根据实际投入另行生成，但不得改变以下依赖关系：

| 里程碑 | 主要交付 | 必须通过的结果 |
| --- | --- | --- |
| M0 基线收敛 | 单 PostgreSQL 集群逻辑隔离方案、部署档位、配置约定、独立迁移、锁定依赖和 CI | 文档、Compose 目标、迁移边界和运行配置一致；平台与示例应用可独立构建 |
| M1 身份与 API | Traefik 基础入口、authentik、OIDC Discovery/JWKS 本地验证、应用注册、用户与权限 API、服务身份、测试通知、审计 | 独立应用完成登录和 API 调用；错误令牌与无权限请求被拒绝；正常请求不逐次依赖 authentik 或平台在线判权 |
| M2 可靠事件 | RabbitMQ、事件契约、应用 Outbox、中继、平台 Inbox、最小只读投影 | 业务与 Outbox 原子提交；重复、重试和消费者重启不会产生重复结果；API-only 应用无事件表和 Worker |
| M3 平台公共能力 | 平台管理端、应用中心、开发者中心、用户组织、角色权限、数据范围、应用凭据、通知和审计 | 平台管理员与应用开发者完成公共能力验收；中性参考应用通过 API-only 与事件接入一致性测试，平台代码中不存在真实领域实现 |
| M4 生产准备 | SLO/RPO/RTO、备份恢复、指标告警、凭据轮换、容量上限、安全与降级演练、运行手册 | 性能、安全、恢复、积压和公共依赖故障演练通过，满足 V1.0 退出条件 |
| M5 多消费方治理 | 多套独立消费方配置、脚手架、兼容窗口和契约治理；按明确需求启动语义目录 | 至少两套彼此独立的接入配置通过认证测试，无需共享源码、数据库或会话；外部业务应用不作为平台交付物 |
| M6 AI 增强 | 评测集、模型与知识接入、受控工具和证据链 | 至少一个低风险用例通过离线评测、权限、人工确认和线上观测门禁 |

关键路径依赖：

1. M0 未通过前不得并行扩展通知渠道、文件、流程、语义或 AI 运行组件。
2. M1 未通过前不得使用临时票据、共享 Cookie、身份头信任或平台数据库账号替代正式身份接入。
3. M2 只能在 M1 的应用身份、scope 和审计可用后验收；Outbox/Inbox 模板不得反向成为 API-only 应用依赖。
4. M3 依赖 M1；其中事件接入一致性验证同时依赖 M2。参考应用只生成业务中性的测试记录，不得以平台数据库直写或领域特例绕过公开契约。
5. M4 必须使用代表性数据量、并发、事件积压和依赖故障场景完成，不能只验证空环境和理想网络；压测数据不得引入真实领域代码作为平台依赖。
6. 语义治理从 M5 按跨应用发现或 AI 数据需求启动，AI 从 M6 启动；二者不阻塞 M0 至 M4。
7. 每个环境分别使用应用登记、回调白名单、凭据、数据库角色和事件权限；生产与非生产不得共用数据和凭据。
8. 各里程碑的任务清单、产物、验证命令和回滚要求以[独立实施计划](implementation-plan.md)为执行基线。

## 22. 分阶段交付工作流

### 22.1 工作流 A：平台产品与契约

- 确定平台产品负责人和各公共能力负责人。
- 冻结版本范围、能力目录、支持的接入模式与非目标。
- 定义平台管理员、应用开发者、安全审计和运维角色的任务与权限矩阵。
- 输出应用注册、身份、权限、通知、审计和事件的公开契约与兼容策略。
- 定义平台 SLO、运维边界、验收用例和发布门禁。
- 组织平台角色验收、文档走查和反馈闭环。

### 22.2 工作流 B：平台研发

- 平台公共服务、API 网关和契约仓库骨架。
- authentik 标准授权流程、用户令牌与公钥接入，以及服务身份、scope 和凭据撤销。
- 用户、组织、权限注册、授权查询和决策 API。
- 独立应用注册、门户入口、回调、健康检查和版本治理。
- 最小消息和审计 API；工作流、统一待办、文件及扩展消息渠道只有正式进入平台产品范围后才启用。
- 版本化 SDK、本地替身和独立示例应用。
- 公共错误、日志和配置。

### 22.3 工作流 C：接入参考与认证测试

- 维护业务中性的 `examples/standalone-app`，仅包含最小测试记录、独立数据库迁移和部署入口。
- 验证用户令牌、服务身份、scope、平台 API 客户端、通知请求和审计链路。
- 分别验证默认 API-only 配置，以及按需开启的事件发布、事件消费和平台投影配置。
- 提供 SDK 示例、本地替身、消费方契约测试和端到端测试。
- 验证参考应用与平台可以分别构建、部署、回滚和发生故障。
- 不实现真实业务字段、状态机、流程、报表或领域页面；任何真实业务应用均在平台项目之外独立立项。

### 22.4 工作流 D：跨应用机制

- 定义公共查询、命令、事件、对象引用和平台投影的治理边界。
- 在 M2 前准备事件契约、本地替身和中性测试夹具，在 M3 前准备稳定候选契约与一致性测试环境。
- 定义公开查询、命令和事件契约。
- 所有应用注册能力、服务身份和最小 scope；手工对象引用可以不调用来源系统，但应用接入平台公共服务仍必须使用服务身份。
- 对启用事件能力的生产者或消费者，分别建设本地 Outbox 或 Inbox、幂等、超时和重试，并验证与业务处理原子提交；API-only 应用不强制建设这些表。
- 提供命令状态、结果核对和人工补偿。
- 未来外部应用实际接入时，再由其登记权威来源、责任人、新鲜度、降级、数据对账和必要的回写边界；这些领域集成不属于平台建设交付物。

### 22.5 工作流 E：企业语义

- M0 至 M4 只维护稳定对象 ID、来源和契约版本约定；本工作流从 M5 或更早出现明确跨应用发现、搜索或 AI 数据需求时启动。
- 建立业务词汇表、命名空间和稳定语义 ID。
- 根据已经批准的跨应用或 AI 用例定义共享对象、属性、状态、关系、权威来源系统和平台访问责任应用，不预建特定领域包。
- 建立 SourceBinding、外部适配来源、映射验证和语义包发布流程。
- 对齐 API、事件、指标、知识和工具引用。
- 执行跨引用、兼容性、敏感字段和变更影响检查。

### 22.6 工作流 F：AI

- M0 至 M5 不把 AI 作为版本退出条件；正式工作流从 M6/V1.2 启动。
- 选择一个低风险、高频、可评测的用例。
- 准备知识和评测集。
- 接入模型和检索。
- 记录引用、反馈和版本。
- 通过功能开关逐步放量。

### 22.7 工作流 G：运维与安全

- 环境和流水线。
- 备份和恢复。
- 日志、指标和告警。
- 应用级连接、并发、队列、超时和配额。
- 独立应用崩溃、慢调用、凭据撤销、积压、重试风暴、公共依赖故障和恢复演练。
- 账号生命周期核对；只有统一待办正式进入平台范围后，才增加在途任务转派和无人待办告警。
- 权限、安全和漏洞测试。
- 发布、回滚和运行手册。
- 运行 RACI、值守、升级、备份人员和交接。

## 24. 验收指标

### 24.1 平台产品指标

- 平台管理员完成用户、组织、角色、应用和凭据配置任务的成功率与耗时。
- 应用开发者仅依赖公开文档、SDK 和沙箱完成首次 API 调用的成功率与耗时。
- API-only、事件发布、事件消费和平台投影接入一致性测试通过率。
- 公开 API、事件与 SDK 的兼容性测试通过率，以及破坏性变更数量。
- 应用凭据轮换、撤销和权限变更在目标时限内生效的比例。
- 平台文档缺陷、接入支持请求和重复人工配置步骤数量。

### 24.2 平台运行指标

- 新场景平均上线周期。
- 公共能力复用率。
- 独立应用从登记到首次通过接入验收的周期。
- 通过正式网关和事件目录接入的应用比例，以及未登记点对点接口数量。
- 独立应用无需平台发版即可发布和回滚的成功率。
- API 成功率和 P95 时延。
- 用户令牌、服务身份和 scope 校验失败率，凭据轮换与撤销生效时长。
- 队列积压和同步失败率。
- Outbox 待发布时长、Inbox 重复命中率、死信数量和人工补偿时长。
- 平台只读投影的 P95/P99 同步延迟、来源版本缺口、过期对象数、对账差异率、补数时长和从空库重建成功率。
- 按应用的连接或查询并发、请求并发、任务队列和配额触顶次数。
- 应用崩溃、慢调用、下游不可用和重试风暴演练中的故障扩散范围。
- 发布频率、失败率和恢复时间。
- 备份恢复演练成功率和实际 RPO/RTO。
- 入转离账号处理 SLA、名册差异数、无人待办数和转派超时数。
- 权限或审计缺陷数量。

### 24.3 语义治理指标

以下指标从 M5/V1.1 实际启用语义治理后开始采集，不作为 V0.1、V0.5 或 V1.0 退出条件：

- 已登记核心语义对象的定义覆盖率。
- 已发布语义包的校验通过率和悬空引用数量。
- 核心 SourceBinding 的 `verified` 比例。
- 语义定义变更的影响分析覆盖率。
- 语义投影的数据新鲜度和重建成功率。
- 外部权威来源、适配应用和对账责任的登记覆盖率。
- AI 查询携带有效来源和版本证据的比例。

### 24.4 AI 指标

以下指标从 V1.2 正式 AI 用例开始验收；V1.0 技术预览只记录数据，不作为版本退出条件：

- 建议采纳率。
- 人工修改率。
- 引用正确率。
- 工具调用成功率。
- 高风险误执行次数。
- 单次运行时延和成本。

第一阶段的成功标准不是接入了多少真实业务应用，而是：

> 平台能够从空环境完成初始化，并在基础与标准事件档位下稳定运行；业务中性参考应用能够在不共享源码、数据库、Cookie 或 Session 的前提下通过身份、权限、通知、审计、API 和事件一致性测试。真实业务应用的开发、数据迁移、领域验收和上线不属于平台建设的退出条件。

## 25. 研发完成定义

一项需求只有满足以下条件才能标记完成：

- 产品验收标准明确且已通过。
- 服务端权限和数据范围已测试。
- 业务规则有自动化测试。
- API 或事件契约已更新。
- 独立应用能够单独构建、测试、迁移和部署，不要求编译平台源码、重启平台或连接平台事务库、平台只读投影库。
- 用户请求已使用本地缓存的 JWKS 验证令牌签名、issuer、audience、有效期和 scope，正常请求不逐次访问 authentik；后台调用使用服务身份，并覆盖无权限、过期、未知 `kid`、身份服务短时不可用和凭据撤销测试。
- 平台公共 API 同时通过提供方契约测试和应用消费方契约测试。
- 涉及可靠生产事件时，已验证业务写入与本地 Outbox 原子提交；涉及产生持久化副作用的事件消费时，已验证 Inbox 或等价幂等记录与业务处理原子提交，并覆盖重复投递测试。仅使用 API 的应用不适用本项。
- 涉及平台只读投影时，已登记业务用途和字段白名单，并测试重复、乱序、版本缺口、删除、过期展示、快照水位、对账及从空投影库重建。
- 已启用语义治理的能力涉及对象、关系、指标、行为或来源含义时，领域语义包和版本已同步更新；未启用语义治理的 V0.1/V0.5 能力只需维护公开契约中的稳定对象 ID、来源和版本。
- 涉及外部来源时，已登记权威来源系统、平台访问责任应用、新鲜度、降级、权限和对账规则，并具备本地替身或测试环境。
- 涉及语义变更时，定义通过 Schema、跨引用、敏感字段和兼容性校验。
- 数据库迁移可从空库执行。
- 日志、指标和关键审计已补充。
- 门户入口、回调地址、API 地址、健康检查、版本和服务身份已按环境登记；启用事件或投影能力时，相应发布、订阅和数据权限也已登记。
- 跨应用调用具备超时和错误处理。
- 涉及组织、角色或账号状态变化时，已测试权限即时生效、历史保留、在途任务影响和转派路径。
- 涉及新应用或高负载入口时，已定义连接、并发、队列、超时、存储和调用预算并接入按应用监控。
- 敏感数据已检查。
- 用户文档和运行手册已更新。
- 已明确发布和回滚方式。
- 已明确运行负责人、告警升级和必要的交接方式。
- 不违反独立项目、公开契约和数据所有权边界。

## 26. 主要风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 平台范围过大 | 第一版长期不能上线 | 固定 V0.5 范围，完整低代码能力后置 |
| 过早抽象领域能力 | 平台在没有稳定共性需求时建设通用流程、表单或领域模型，造成返工 | 初期只建设已确认的公共机制；工作流、表单和语义能力必须按独立平台需求与验收标准立项 |
| 平台侵入应用领域 | 平台出现真实业务字段、状态机、规则或可写业务表 | 以模块边界测试、数据库权限和代码评审强制平台只保存公共配置与可重建投影 |
| 平台公共服务成为巨型单体 | 平台内部模块互相调用和写表 | 平台内部保持模块边界、Schema 和边界测试；业务应用始终在独立项目中 |
| 平台团队成为瓶颈 | 所有需求排队 | 平台团队负责机制，领域团队负责应用 |
| 形式上独立、实际上强耦合 | 应用仍共享平台源码、Cookie、Session 表、数据库账号或同一发布流水线 | V0.1 用独立示例应用验证分开构建部署、令牌、服务身份、API、事件和数据库边界 |
| 统一身份接入不安全 | 自制临时票据、长期密钥或错误的 audience 导致冒用 | 采用标准授权流程和成熟实现，短期令牌、公钥轮换、scope、服务身份、撤销和安全测试从 V0.1 建设 |
| 身份或权限成为逐请求单点 | 每次验证令牌或普通判权都访问 authentik 或平台，短时故障导致全部应用不可用 | JWT 使用本地 JWKS 缓存验证，应用授权使用带版本和期限的缓存，对象级权限本地执行；高风险在线决策失败关闭 |
| 平台 API 成为同步单点 | 权限、消息或文件服务抖动拖慢所有应用 | 公布 SLO 和降级语义，应用设置超时熔断；权限缓存有版本和短期限，高风险写操作失败关闭 |
| SDK 与平台契约漂移 | 应用升级后批量失败或被迫同步发版 | SDK 独立版本化、兼容窗口、提供方与消费方契约测试，不在 SDK 内嵌平台实现 |
| 集成机制被过度标配 | 只调用少量平台 API 的简单应用也被要求维护消息表、中继、死信和补数 | 默认只启用 `API_CLIENT`，按业务可靠性需要组合事件发布、事件消费或投影能力，并由 Integration Kit 提供样板实现 |
| 投入能力与版本范围不匹配 | 接入面、独立应用、跨应用、运维和 AI 同期展开，导致所有能力都无法验收 | 严格按 M0 至 M6 门禁推进；资源变化只调整日历时间，不并行跳过安全、契约和恢复条件 |
| 外部应用契约延期 | 后续跨应用功能无法按期联调 | 平台用中性契约和本地替身完成机制验收；外部应用接入单独排期，未通过时不得以数据库直连或平台领域特例过渡 |
| 外部主数据边界不清 | ERP/MES 被误当成平台应用或被复制为第二主库 | 登记权威来源系统和领域适配应用，仅发布受治理契约或可重建投影，定义新鲜度、降级和对账 |
| 应用业务数据重复 | 多套数据可独立修改并产生不一致 | 明确数据拥有应用，其他应用只保存稳定引用和必要只读快照 |
| 平台投影变成第二业务主库 | 平台直接改投影、业务逻辑依赖投影强一致或把所有字段复制到平台 | 投影只读、字段白名单、显式新鲜度；写操作和关键判定回到应用 API，投影必须可从来源重建 |
| 增量投影长期漂移 | 事件重复、乱序、漏投或全量与增量水位不连续 | Inbox 去重、对象版本保护、缺口检测、快照水位、周期对账、补数和从空库重建演练 |
| Outbox/Inbox 错误集中化 | 平台试图扫描所有应用数据库或应用无法原子写中央表 | Outbox/Inbox 位于生产者和消费者各自数据库并与业务同事务；中继运行在应用边界，中央只保留运营投影 |
| 本体范围过大 | 建模周期阻塞平台公共能力交付 | V0.1/V0.5 只维护稳定 ID、来源和普通数据契约，语义目录、SourceBinding 和运行能力从 V1.1 按明确用例启动 |
| 语义对象等同数据库表 | 领域模型和数据绑定重新耦合 | 对象定义、SourceBinding、业务表和语义投影分离 |
| 语义与运行配置重复 | 权限、流程或规则出现两套真相 | 本体只保存契约和引用，IAM、工作流和规则引擎负责执行 |
| 未验证映射被 AI 使用 | AI 基于错误口径回答或行动 | 显示绑定状态，生产决策优先使用 verified 数据并保留证据 |
| 语义变更失控 | API、事件、工具和 AI 同时失效 | 不可变版本、兼容性校验、影响分析和迁移窗口 |
| AI 效果不可控 | 输出错误或越权 | 从 L0/L1 开始，评测、人工确认和工具最小权限 |
| 身份映射生命周期失控 | authentik 账号、平台用户、组织角色、授权缓存和在途任务状态不一致 | 明确入转离 SLA、同步重试、差异对账、授权版本失效和审计；定期验证上游身份源与 authentik 联邦配置 |
| 人员变化产生无人待办 | 权限已撤销但历史任务仍指派给离职或转岗用户 | 权限立即生效，生成在途影响清单和强制转派队列，临时对象授权有审批和到期时间 |
| 持续运营能力不足 | 告警无人处理、数据口径无人审核、上线后无法迭代 | V1.0 前确认运行 RACI、值守、备份人员、每周容量、升级和交接安排 |
| 缺少真实消费反馈 | 平台契约在参考环境通过，但不适合后续应用接入 | 邀请独立应用开发者参与文档与沙箱验收，记录接入摩擦；真实应用仍按独立项目治理，不纳入平台交付物 |
| 单应用拖垮公共服务 | 调用风暴、事件积压、超大文件或任务重试占满网关和共享服务 | 在网关、事件、消息和文件服务按 application_id 设置限流与配额，支持单应用凭据停用并演练 |
| 移动端范围蔓延 | 架构图被理解为第一阶段必须交付移动端 | V0.5/V1.0 仅承诺桌面 Web；手机浏览器、原生端和小程序按独立需求与验收排期 |
| 环境成本或混用 | 维护对象过多，或测试与生产互相污染 | 使用本地或临时开发、共享集成、按需 UAT 和隔离生产，按逻辑职责而非等规模资源建设 |
| 逻辑隔离被误解为共享写权限 | 共用 PostgreSQL 集群后出现跨 Schema 查询、共用账号或联合迁移 | 每个数据库或 Schema 使用专用角色、连接池和迁移；禁止跨边界授权并加入自动化权限检查，达到 SLO 或合规阈值时再物理拆分 |

## 27. 启动前必须确认的事项

以下事项会影响代码和排期，应在 V0.1 启动前或最晚在对应功能开发前确认：

截至 V2.0，后端语言与核心组件已经冻结：自研后端使用 Python 3.14、FastAPI、Pydantic、SQLAlchemy、Alembic 和 uv；身份使用 authentik；基础接入使用 Traefik；数据库和事件基础设施分别使用 PostgreSQL 18 与 RabbitMQ 4.2；默认使用单 PostgreSQL 集群逻辑隔离；V0.1 不引入通用工作流引擎或语义运行平台。以下条目仍需补充环境参数、SLO、责任人和运行细节，不得重新以未决事项为由混入 Java 或 Node.js 后端。

1. `[技术栈已冻结]` 平台与独立应用的仓库、构建、制品、发布、Python 包仓库和版本约定。
2. 部署环境是本地数据中心、私有云还是混合部署。
3. V0.1、V0.5 和 V1.0 的开发、集成测试、按需 UAT 和生产环境如何实现逻辑隔离；每个环境的 `application_id`、入口、回调白名单、API 地址、凭据、scope、配额和事件权限如何分离；以及正式支持的桌面浏览器范围。
4. `[签发方已冻结为 authentik]` OIDC 签名算法、公钥缓存、issuer、audience、有效期、刷新、撤销、登出传播和密钥轮换参数。
5. 服务身份的凭据形式、保管方、最小 scope、轮换周期、紧急停用、泄露响应和审计规则。
6. `[核心组件已冻结]` Traefik、RabbitMQ、PostgreSQL 平台投影 Schema、契约目录和 Python SDK 的 SLO、兼容窗口、限流及降级语义，以及生产镜像补丁版本或摘要的锁定与升级规则。
7. 平台用户名规则、初始管理员、密码策略及首批用户和组织数据。
8. 入职、转岗、离职和紧急停用 SLA，人工名册核对来源、频率、负责人，以及在途任务转派规则。
9. 企业身份源和 SSO 的重新评估触发条件、决策人和最晚复核版本。
10. authentik、Traefik、RabbitMQ、对象存储、日志监控和 CI/CD 的实际部署位置、持久化、备份、升级和运行责任；工作流、搜索和语义运行服务不得作为 V0.1 隐含依赖。
11. 平台产品负责人、公共能力负责人，以及首批参与一致性验收的平台管理员、应用开发者、安全和运维代表。
12. 中性参考记录与投影的字段白名单、事件版本、快照水位、新鲜度、保留、对账和重建负责人；真实领域数据不作为 V0.1/V0.5 前置条件。
13. M2、M3 门禁所需的 API/事件候选契约、本地替身、测试夹具和一致性测试环境；未来外部应用的联调计划单独管理。
14. 数据等级、审计保留期、RPO 和 RTO。
15. 企业常用消息渠道、平台用户与渠道账号的映射方式，以及通知请求、投递回执和失败补偿契约。
16. 平台版本范围、公共服务中断影响、SLO 和成功指标；投入容量仅用于生成日历计划，不改变能力门禁。
17. V1.0 的平台运行、应用、流程、数据、协作、安全责任 RACI、值守、备份和升级路径。
18. V1.1 启动前的企业语义命名空间、稳定 ID 和领域包负责人；V0.1/V0.5 只冻结普通契约中的对象 ID 和来源格式。
19. V1.1 或首个正式语义/AI 用例启动前由谁审核 SourceBinding、权威来源、指标口径和跨领域关系。
20. 各应用和平台公共服务的连接、并发、队列、查询、存储和调用预算，以及网关、身份、事件、消息和文件服务的共享故障域与容量隔离方案。

这些事项未全部明确时，研发可以按[独立实施计划](implementation-plan.md)先完成平台服务边界、中性参考应用骨架、公开接口契约和本地替身实现，但不能以临时身份票据、共享会话、共享数据库账号或未治理的直连方式进入正式生产。

## 28. 架构决策记录建议

以下关键决策应分别建立 ADR，并在发生变化时记录原因：

- ADR-001：统一平台登记、提供入口并治理公司内部自研应用，但不承载业务应用代码；ERP/MES 等外部系统通过自研适配应用接入，不被平台接管为内部业务模块。
- ADR-002：平台负责通用机制，应用负责业务语义、数据、规则、状态和结果。
- ADR-003：平台公共服务内部初期可以采用模块化单体；业务应用从第一阶段起就是独立项目、独立运行单元和独立发布单元。
- ADR-004：默认使用一个 PostgreSQL 集群承载隔离的 authentik、平台、平台投影和应用逻辑数据库或 Schema；各边界使用独立角色、连接池和迁移，不形成跨库或跨 Schema 写入权，物理拆分由合规、容量、RPO、RTO 或故障域触发。
- ADR-005：应用拥有业务数据，平台拥有通用数据。
- ADR-006：跨项目和跨应用禁止直接读写对方数据表或依赖内部实现。
- ADR-007：跨应用采用公开 API、命令和事件；Outbox/Inbox 按事件发布和消费能力启用，启用后分别位于本应用数据库或隔离 Schema，并与对应本地业务处理原子提交；API-only 应用不强制建设。
- ADR-008：文件、日志、分析和向量数据不进入业务主库。
- ADR-009：工作流状态与业务状态分离。
- ADR-010：AI 仅通过注册工具执行业务操作。
- ADR-011：企业语义层是共享契约，不是业务主库或实例写入入口。
- ADR-012：领域应用拥有具体语义，平台拥有元模型、校验、版本和发现机制。
- ADR-013：语义定义、业务实例、只读投影和执行引擎分离。
- ADR-014：第一阶段使用轻量元数据模型，不强制图数据库或 RDF/OWL。
- ADR-015：AI 查询和动作必须绑定语义版本、数据版本、当前权限和证据链。
- ADR-016：外部主数据保留外部权威源，通过领域适配应用、受治理契约或可重建投影进入平台。
- ADR-017：第一阶段由 authentik 管理账号、凭据、会话和令牌，平台管理用户映射、组织和业务授权；应用使用本地 Discovery/JWKS 缓存验证令牌和版本化授权缓存，不在普通请求中逐次依赖身份或权限服务；两侧配套入转离 SLA、差异对账和缓存失效门禁。
- ADR-018：业务应用的进程和发布故障域从第一阶段起与平台隔离；API 网关、身份、事件、消息和文件等共享基础设施仍需明确 SLO、默认资源上限、降级和故障扩散边界，应用级精细配额在出现明确争用后启用。
- ADR-019：V0.5/V1.0 正式支持桌面 Web，移动端、小程序和完整移动 Web 适配按独立需求启动。
- ADR-020：环境按开发、集成、UAT 和生产的逻辑职责分阶段建设，不要求四套同规模常驻基础设施。
- ADR-021：V1.0 聚焦生产和跨应用加固，正式 AI 能力在 V1.2 通过评测后上线。
- ADR-022：平台公共能力只通过受版本治理的 API 和事件提供；用户请求采用短期用户令牌，后台调用采用独立服务身份，二者不得混用。
- ADR-023：SDK 只封装令牌验证、API 客户端、事件信封和可靠性模板，不包含平台内部实现；公开契约及其兼容策略是应用集成的事实来源。
- ADR-024：平台负责用户、组织、权限项注册和通用授权决策，应用仍负责领域规则、资源归属和对象级授权，并在本地执行最终校验。
- ADR-025：应用业务库是唯一可写真相；平台只保存自身领域数据，以及通过应用事件增量、快照回填和周期对账生成的可重建只读投影，禁止平台直连应用业务库同步表。
- ADR-026：所有自研后端统一使用 Python 3.14、FastAPI、Pydantic、SQLAlchemy、Alembic 和 uv；Node.js 只用于 Vue 构建，后端不引入 JVM。
- ADR-027：authentik 是凭据、会话、OIDC/OAuth2 客户端、签名和撤销执行真相；平台只维护身份映射、组织和业务授权，不自建密码与令牌服务。
- ADR-028：Traefik 是基础设施入口，只承担 TLS、路由、请求大小和必要基础限流；Python 平台接入模块执行应用身份、scope 和审计，应用级精细配额按共享资源保护需求启用；V0.1 不自研通用网关。
- ADR-029：V0.1/V0.5 不部署通用流程引擎、统一流程端口或待办运行服务；后续只有形成明确的平台产品需求、数据边界和验收标准后才能立项，并通过无 JVM ADR。
- ADR-030：实施按 M0 至 M6 能力门禁推进，不以固定团队规模或周数改变架构；V0.1/V0.5 不建设语义运行平台，语义与 AI 分别从明确的复用和可评测用例启动。
- [ADR-031](adr/ADR-031-standard-single-node-production-tier.md)：M4 实测满足已批准的企业 B 端工作时段目标，首个生产部署继续采用 `STANDARD_SINGLE_NODE`；达到 SLO、RPO、RTO、容量、维护或法规触发条件时再升级高可用。

## 30. 最终研发基线

后续开发必须遵守以下二十五条基线：

1. 统一平台负责登记、入口、发现和治理公司内部自研应用，不承载业务应用代码；外部企业系统只能通过登记的自研适配应用或数据网关接入。
2. `STANDALONE_APP` 是 P0、默认且第一优先级的业务应用模式，每个应用拥有独立仓库、构建、制品、运行单元、发布、回滚和运行责任；平台模块不登记成业务应用，未来 `PLATFORM_EXTENSION` 必须另行设计和立项。
3. 一个场景不等于一个应用，应用按照业务领域聚合；平台负责通用机制和统一治理，应用负责业务语义、数据、规则、状态和结果。
4. 平台公共服务内部初期可以采用模块化单体，但不得因此把业务应用合入平台进程、源码仓库或发布流水线。
5. 用户、组织、权限、消息、文件、工作流适配和审计等公共能力只通过受版本治理的 API 和事件提供，应用不得依赖平台内部类库、Cookie、Session 表或数据库。
6. 用户请求使用限定 issuer、audience、有效期和 scope 的短期用户令牌，并通过本地 Discovery/JWKS 缓存验证；普通请求不得逐次访问 authentik 或平台权限服务。后台调用使用可轮换和可撤销的服务身份；平台提供通用授权决策，应用缓存版本化授权并执行领域规则和对象级最终授权。
7. 默认使用一个 PostgreSQL 集群承载隔离的逻辑数据库或 Schema；应用拥有专用角色、连接池、业务表、迁移、备份和恢复责任，平台服务不得使用应用数据库账号。物理拆分由合规、容量、RPO、RTO 或故障域要求触发。
8. Outbox/Inbox 按接入能力启用：可靠事件生产者的业务写入与本地 Outbox 同事务，产生持久化副作用的消费者将 Inbox 或等价幂等记录与业务处理同事务；仅使用 API 的应用不强制建设，中央协作记录不能替代本地原子执行真相。
9. 应用不直接读写其他应用的数据表或依赖其内部实现；跨应用协作只通过公开 API、命令和业务事件完成。
10. 所有公开 API、事件和 SDK 都必须版本化、具备兼容窗口，并通过提供方与消费方契约测试。
11. 应用业务库是唯一可写真相；平台只保存自身领域数据和按已登记用途生成的只读投影。增量走领域事件，全量或重建走带水位快照，投影必须幂等、可对账、可从空库重建且不得反向写应用。
12. 外部数据必须同时声明权威来源系统、平台访问责任应用、新鲜度、降级和对账规则。
13. 工作流状态和应用业务状态分离，身份或组织变化不得静默留下无人待办。
14. 动态 JSON 不能替代正式领域模型。
15. 平台统一元模型和语义治理机制，领域应用和数据负责人拥有具体业务语义。
16. 企业语义采用“数据语义—行为语义—场景编排”三层模型，版本、来源、权限、证据和审计横向贯穿三层。
17. 语义定义、业务实例、只读投影和执行组件必须分离；所有核心语义对象必须声明稳定 ID、权威来源系统、平台访问责任应用、数据负责人和版本。
18. authentik 是凭据、会话、令牌签发和撤销执行真相；平台身份映射必须配套入转离 SLA、状态同步、授权缓存失效和在途任务转派，应用不得接收密码或读取身份系统内部表。
19. 独立应用进程故障不得直接带崩平台或其他应用；对网关、身份、事件、消息和文件等共享故障域必须设置 SLO、安全默认上限、超时、熔断和降级策略，按应用精细配额在明确争用后启用。
20. V0.5/V1.0 只承诺桌面 Web；各环境必须使用不同的应用登记、回调白名单、凭据、权限、配额和数据边界。
21. AI 查询必须保留语义版本、数据来源和证据；AI 写入只能通过受控工具，高风险操作必须人工确认并具备权限、幂等、审计和业务纠正方案。正式 AI 能力从 V1.2 起按评测门禁上线。
22. 第一优先级是让业务中性参考应用通过平台 API、身份、权限、通知、审计和按需事件能力完成接入一致性验证；真实业务应用不属于平台交付物，语义和 AI 运行能力不得阻塞 V0.1、V0.5 或 V1.0。
23. 所有自研后端统一使用 Python 3.14、FastAPI、Pydantic、SQLAlchemy、Alembic 和 uv，按请求或消息任务隔离 `AsyncSession`；Node.js 只用于 Vue 构建，服务端不引入 JVM。
24. V0.1 使用 PostgreSQL、RabbitMQ、Traefik 和 authentik，不引入 Celery、Redis、Kafka、Elasticsearch、Temporal、通用 BPMN 引擎或自研 Python 网关；新增基础设施必须由已验证需求和 ADR 驱动。
25. 部署提供基础接入、标准事件和高可用三档；档位由已确认的事件能力、SLO、RPO、RTO、合规和故障域选择，不因预计用户增长默认启用高可用或微服务化。
