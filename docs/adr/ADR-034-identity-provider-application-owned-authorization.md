# ADR-034：AI Hub 只提供企业身份，业务应用自主授权

- 状态：已接受
- 决策日期：2026-09-01
- 接受日期：2026-09-01
- 决策范围：独立业务应用使用 AI Hub 登录、同步员工目录、初始化首个管理员时，身份与功能授权的系统边界

## 背景

独立应用需要获得类似 “Sign in with Google” 的体验：员工使用统一企业账号登录，应用获得稳定用户标识和必要的基本资料。同时，业务角色、菜单权限、操作权限、数据范围和对象归属具有强烈的应用语义，不应要求 AI Hub 认识每个应用的功能模型。

旧的接入方式允许应用读取 `/me/permissions` 并调用 `/authorization/decisions`，容易使应用把 AI Hub 的权限定义当作业务授权事实来源。这样会把应用发布、业务角色变更和平台治理绑在一起，也让 AI Hub 成为所有业务请求的在线依赖。

应用还面临两个初始化问题：第一个管理员从哪里来，以及如何安全地同步可授权的员工名单。

## 决策

**AI Hub 是企业 OIDC 身份提供方和员工目录来源；每个独立业务应用是自身功能授权的唯一事实来源。**

约束如下：

1. **登录只交换身份。** 用户通过 OIDC Authorization Code + PKCE 登录。应用验证令牌后可调用 `/platform-api/v1/me` 获取 `user_id`、`subject`、姓名、邮箱、组织和账号状态。登录成功不等于拥有任何业务权限。
2. **业务授权留在应用。** 角色、功能权限、数据范围、对象归属、审批规则和会话失效版本都存储并判定在业务应用本地。身份型应用不得登记 `dsh_work.*` 一类业务权限，也不得依赖 `/me/permissions` 或 `/authorization/decisions`。
3. **登记人、负责人和初始管理员相互独立。** 平台登记人是创建应用记录的 AI Hub 操作员，只用于审计；应用负责人从活动员工目录中选择，承担业务治理和联络责任，但不因此获得业务应用权限；每个环境必须从活动员工目录中独立选择一名初始管理员。平台角色不是后两者的候选资格来源。
4. **初始管理员按环境一次性领取。** 环境创建时生成一条 `PENDING` 管理员 Bootstrap。明确指定的初始管理员登录后以用户令牌调用 `POST /applications/{application_id}/environments/{environment}/admin-bootstrap`；首次成功变为 `CONSUMED`，同一用户重试幂等。业务应用据此在本地幂等创建首个超级管理员。
5. **负责人和 Bootstrap 不联动。** 负责人变化永远不修改任何环境的初始管理员。`PENDING` 状态可由有权管理应用的操作员显式改选并留下审计事件；`CONSUMED` 状态锁定为历史事实，后续授权只能在业务应用本地调整。
6. **员工目录单向同步。** 具有 `platform.directory.read` 的应用服务身份可调用 `/platform-api/v1/directory/users`，按不透明、提交顺序串行化的目录修订 cursor 增量读取员工基本资料和状态。目录不返回平台角色、应用角色、权限或数据范围；`updated_at` 仅表示资料更新时间，不作为消费位点。
7. **停用或平台账号作为墓碑。** `business_user=false` 明确区分 AI Hub 平台账号与业务员工；目录项在身份停用或不再属于业务用户时返回 `tombstone=true`。业务应用应禁止其新登录、撤销活动会话并从员工授权列表排除，但保留审计历史和本地授权记录；若重新成为有效业务员工，再由本地策略决定是否恢复访问。
8. **默认无权限。** 新同步员工只建立外部身份映射，默认没有任何本地角色。管理员必须在业务应用管理端显式授权。
9. **环境隔离。** Bootstrap 消费状态、应用服务凭据、目录同步 cursor 和本地管理员资格均按环境隔离。生产与非生产不得共享密钥、Cookie 或本地授权数据库。

## 公开契约

| 目的 | 调用方 | Scope | 接口 |
| --- | --- | --- | --- |
| 当前员工身份 | 用户令牌 | `ai_hub.identity platform.me.read` | `GET /platform-api/v1/me` |
| 领取初始管理员 | 用户令牌、环境指定的初始管理员 | `ai_hub.identity platform.application.bootstrap` | `POST /platform-api/v1/applications/{application_id}/environments/{environment}/admin-bootstrap` |
| 增量同步员工 | 应用服务令牌 | `ai_hub.identity platform.directory.read` | `GET /platform-api/v1/directory/users` |

业务应用必须将 `AI Hub user_id` 作为外部身份稳定键；`subject` 用于登录映射并随目录同步更新。邮箱和姓名均不是授权键。

## 备选方案（未选择）

### 在 AI Hub 为每个业务应用维护全部权限

未选择。平台会被迫理解所有应用的菜单、数据范围和对象状态，应用发布需要同步修改平台权限，形成双写和强耦合。

### 管理端使用另一套密码账号

未选择。它增加凭据生命周期、MFA、离职停用和审计成本。管理端继续使用 AI Hub OIDC；“独立”指授权存储和判定独立，而不是重复建设认证。

### 用固定环境变量指定首个管理员邮箱

未选择。邮箱可变且缺少集中审计，多个环境容易漂移。从员工目录按环境选择初始管理员并使用一次性 Bootstrap，可提供稳定 UUID、显式状态和幂等恢复，同时不把负责人职责等同于系统权限。

## 后果与风险控制

| 后果或风险 | 控制措施 |
| --- | --- |
| 应用本地授权配置错误 | 本地权限版本、管理审计、最小权限角色、危险操作二次确认 |
| Bootstrap 在跨系统写入间失败 | AI Hub 对同一领取人幂等返回；应用本地角色写入也必须幂等，可安全重试 |
| 员工资料同步中断 | 持久化不透明 cursor、分页重试、记录最后成功时间；不影响已登录用户的本地授权判定 |
| 离职账号仍有会话 | tombstone 同步和登录时 `/me` 状态检查均触发本地会话撤销 |
| 目录接口暴露过多员工信息 | 仅应用绑定的服务身份、专用 scope、最小字段集和平台审计 |
