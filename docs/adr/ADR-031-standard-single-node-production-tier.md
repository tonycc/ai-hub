# ADR-031：首个生产档位继续采用标准单节点

- 状态：已接受
- 决策日期：2026-08-14
- 决策范围：平台首个生产部署档位
- 权威目标：[`deploy/operations/production-targets.json`](../../deploy/operations/production-targets.json)

## 背景

平台面向企业 B 端和内部工作时段应用，优先目标是业务正确、权限清晰、稳定可恢复和部署维护简单。M4-01 先批准了 `STANDARD_SINGLE_NODE` 基线，M4-02 至 M4-05 随后完成恢复、告警、发布回滚、凭据轮换、性能、安全和公共依赖故障演练。M4-06 必须根据这些实测结果决定是否在首个生产环境启用高可用，而不能仅根据预估用户增长增加基础设施。

当前档位是单台受管 Linux 主机上的 Docker Compose：Traefik、authentik、平台模块化单体、门户和按需 RabbitMQ 共享主机；一个 PostgreSQL 实例承载相互隔离的逻辑数据库和 Schema。独立业务应用仍是平台外的独立项目与部署单元，不因本 ADR 被并入平台进程或数据库权限边界。

## 决策

首个生产部署继续采用 `STANDARD_SINGLE_NODE`，本阶段不升级高可用档位，不引入 Kubernetes，不拆分平台模块化单体，也不部署 PostgreSQL 或 RabbitMQ 集群。

生产实例必须同时满足以下约束：

1. PostgreSQL、authentik 文件数据和平台所辖数据库使用已演练的加密备份流程，并写入主机故障域之外的存储。
2. 生产入口使用正式 HTTPS 域名和独立密钥；监控、备份和告警定时器安装到主机并绑定已确认责任人。
3. 发布继续使用不可变制品、expand 兼容迁移、隔离金丝雀和镜像回滚；独立应用不进入平台发布清单。
4. 在目标生产主机上线前重跑静态门禁、负载门禁和恢复演练。开发机结果用于架构决策，不能替代目标主机证据。

## 容量与恢复证据

| 维度 | 批准基线或触发条件 | M4 实测 | 判断 |
| --- | --- | --- | --- |
| API 基线负载 | 至少 20 RPS、1000 请求 | 25.015 RPS、1000 请求 | 当前档位满足批准基线 |
| API 延迟 | p95 ≤ 500 ms、p99 ≤ 1500 ms | p95 14.815 ms、p99 23.045 ms | 当前基线有明显延迟余量 |
| API 错误 | 5xx ≤ 1% | 0%，无传输错误 | 通过 |
| 核心恢复 | RTO ≤ 120 分钟 | 全服务 945 秒恢复 | 通过 |
| 消息恢复 | 关键积压 15 分钟内排空 | 1501 条在 6 秒内排空 | 通过 |
| 公共消息依赖 | 中断时事实不丢失 | RabbitMQ 恢复后 6 秒完成投递和投影 | 通过 |
| HA 容量触发 | 持续公共 API 负载超过 100 RPS | 本轮只证明 25.015 RPS 门禁，不存在已批准的 100 RPS 持续需求 | 未触发 |

25.015 RPS 是按批准门禁执行的结果，不是容量上限测试。该结果不能外推为系统最多只能处理 25 RPS，也不能外推为已经验证 100 RPS。容量承诺仍以目标环境、代表性数据和实际持续负载的重复测量为准。

## 高可用触发评估

决策时没有任何已批准触发条件成立：

- 服务目标仍为工作时段 99.5%，没有提高到 99.9% 或 7×24。
- 核心数据目标仍为 RPO 60 分钟、RTO 120 分钟，没有收紧到 RPO 5 分钟或 RTO 30 分钟。
- 没有超过 100 RPS 的持续公共 API 需求或实测流量。
- 计划维护可安排在服务窗口外，业务尚未声明单主机维护不可接受。
- 没有法规或合同要求把数据库、消息和入口部署到不同物理故障域。

任一条件被正式批准，或连续观测显示当前档位无法满足 SLO 时，必须重新打开本 ADR；不得通过临时提高超时、隐藏告警或删除积压来维持单节点结论。

## 未选择的方案

### 立即建设全套高可用

未选择。它会同时引入多主机网络、数据库选主、消息副本、集中监控、证书与密钥分发及独立恢复流程，但当前没有 SLO、RPO、RTO、容量或合规证据要求承担这些运行成本。

### 仅把无状态组件扩为多实例

未选择为首发默认档位。单独增加 API/门户实例不能消除 PostgreSQL、RabbitMQ 和宿主机故障域；在单主机上复制进程也不构成高可用。若仅出现 CPU 或并发压力，可先在同一架构内做受测的纵向扩容或 Worker 扩容，并保留相同契约。

### 立即迁移 Kubernetes 或拆分微服务

未选择。编排方式和模块拆分都不能直接满足数据恢复目标，反而会增加发布、观测和故障定位面。未来升级高可用时仍可保持平台模块化单体。

## 后果与风险控制

| 后果或风险 | 控制措施 |
| --- | --- |
| 主机意外故障会造成整个平台中断 | 异机加密备份、已演练整机恢复、120 分钟 RTO、P0 告警和明确升级责任 |
| PostgreSQL 是身份、平台和参考运行数据的共同物理故障域 | 逻辑数据库、角色、迁移和连接池继续隔离；数据库是首次 HA 升级的优先对象 |
| 单节点 RabbitMQ 不能在主机故障时保持在线 | 发布方使用 Outbox 与 confirms，消费者使用 Inbox/DLQ；恢复后按运行手册重放和对账 |
| 共享主机可能发生 CPU、内存、连接或磁盘争用 | 采集 OpenMetrics、队列和数据库指标；达到告警或持续容量触发条件时进入容量评审 |
| 发布和主机维护可能短时不可用 | 安排在服务窗口外，提前通知，使用金丝雀、回滚和发布前恢复点 |

升级顺序固定为：优先采用外部托管或独立高可用 PostgreSQL及异机备份，其次把 Traefik、平台 API、门户和必要 Worker 扩为跨主机实例，最后按事件持续性要求部署 RabbitMQ 多节点。每一步都必须有新的故障域图、容量证据和恢复演练，不自动触发业务模块拆分。

## 复核机制

- 上线前：在实际主机重跑完整 CI、M4 韧性门禁和恢复演练。
- 每月：复核服务窗口内可用性、p95/p99、5xx、峰值与持续 RPS、数据库连接/存储和队列积压。
- 每季度及每次重大版本后：执行恢复、回滚和凭据轮换抽验。
- 任一 HA 触发条件、重复 SLO 违约、无法在 15 分钟内清空代表性积压或无法在 RTO 内恢复时：停止容量承诺，重新评审本 ADR。
